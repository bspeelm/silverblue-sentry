# sentry: Silverblue monitor & maintenance TUI (Rust + ratatui)

Spec: `docs/spec.md`. Binding amendments: `docs/spec-addendum.md` (read both before changing behavior).
Design for M3–M7: `docs/design/m3-m7.md`. Design for `sentry config` (one writer, a setup flow, a Config tab, a wizard; built in four parts, all done): `docs/design/config.md`. Design for SusCheck in sentry (a server's screen `8`, reading a household's checks, which never reach Claude): `docs/design/suscheck.md`.
Visual target: `docs/design/sentry-tui.dc.html` (read the source; don't render it).
Upgrade procedures: the user's personal notes in `docs/cheatsheets/` (gitignored, never commit or publish them) are the source for `assets/workflows/*.toml`.

## Layout
- Cargo workspace, one repo: `crates/sentry-core` (shared: exec, paths, config, baseline, finding, claude, maint records, workflow format + runner, disk/gpu/journal/net/procfs parsers, the TUI kit incl. the frame, chat, docview, maintlist, records), `crates/sentry-app` (what targets share beyond the kit: the app itself, below, and `remote/`: a host over ssh), the targets `crates/sentry-local` (this machine), `crates/sentry-server` and `crates/sentry-network` (libraries, each with a `testing` feature for the window's tests), and `crates/sentry`, the one binary (`main.rs` this machine's commands, `server.rs` the server's, `network.rs` the network's, `tui.rs` the window, `tests.rs` the targets side by side). Core never depends on the others; `sentry-app` depends only on core; targets never depend on each other; only `crates/sentry` depends on all three.
- One program, three names: called as `sentry-server` or `sentry-network` (argv[0]: the symlinks `make install-binary` makes beside it) or as `sentry server …` / `sentry network …` it is that command line (`main.rs` `as_command`), same output. A workflow step that runs `sentry-server cond …` finds it beside the program (`remote::workflow::exe`: `sentry server`); Claude's profiles call `sentry-server run|exec` from PATH (the symlink).
- `sentry-local` re-exports core under the old names (`crate::exec`, `crate::maint::log`, …); its `maint`, `workflows`, `collectors`, `tui` modules glob-re-export core's and add their own. sentry-server uses `sentry_core::…` explicitly (its own `config`/`maint`/`tui`/`audit` would clash).
- `crates/sentry-app/src/remote/` (moved out of sentry-server, which re-exports them under its old paths): `mod.rs` `Remote { name, host, scope, privilege, hold_stdin }` (`Privilege::Sudo { allow }`: `sudo -n` through the allowlist; `Privilege::Root`: bare argv, `sudo_mode()` is `SudoMode::Root` without an exec; `Remote::dropbear()` sets `hold_stdin`, see sentry-network), `Error` (the server's `SrvError`), `host`; `workflow.rs` (`Session` with a `Box<dyn Env>` and the program's name, `Session::on(Words)` for what it calls its host (default "the server"), `Exec`, `Live`, `tee_to`, `no_prompt`, `root`/`own_dir`/`pick_dir`); `probe.rs`; `recorder.rs` (`record(r, extras)`); `audit.rs` (`Report<S>`, the report store, `set_expected*`, `pattern_for(ns, …)`, `listener_status`/`listener_id`); `gateway.rs` (`SECRET`, `Held`, `words`/`commands`, `run_cli(prog, r, line, policy)`, the read queue); `upstream.rs` (GitHub, endoflife.date, `comparable`); `wfview.rs` (screen `0` for a host whose runs are `Session`s: the list, the run, its card, in the run's own words; sentry-network uses it).
- `crates/sentry-app/src/` is the app (`sentry_app::App`, a slot per target): `target.rs` (`Target` with `Upkeep`/`Asks`/`Host`, object-safe: a target owns its fetch threads, kinds, store and screens; `Ident` its names and words; `Ways` where a program's flows go their own way: words and rules such as `auto_polled` and `reboot_ends_tui`, default = the server's, each flow asks `self.ways`; `Cx` what it may look at, incl. `at`, the one clock (`Win.at`, the event's instant), and `focused` (the target has the window: only then may `due`/`next_due` poll for its screen); `Mail` how its threads and streams answer, tagged with its id; hooks with a default for what only one program does: `on_prompt`, `pane_ended`, `plan_key`, `plan_written`, `chat_continue`, `wf_start`, `session_starts`, `run_cmd`, `run_plan`/`run_info`, `find_workflow`), `app.rs` (`App { slots, focus, win }`, `App::new` + `App::add`; `Win`: theme, keymap, toast, the input line, the help/quit box; `Event` carries a target id; `App::with(i, …)` runs a slot's flow with the window as that slot sees it), `slot.rs` + `slot/` (`Slot`: one target, its `Shared` records, the screen in view, run, session, series, chat, writer, Records, its boxes; every flow is an `impl Slot` method taking `&mut Win`: `core` events/keys/`open()`/prompts, `effects`, `session`, `wf`, `series`, `review`, `records`, `draw`), `shared.rs`, `effect.rs` (`Effect`, `Prompt`, `WfCmd`; a target's own effects travel as `Effect::Own` and come back in `Target::on_own`/`after_suspend`), `run.rs` (`WfRun`: a workflow run as the app sees it; `remote::workflow::Session` is one, sentry's `tui/wf.rs` `Session` the other; `Exec::Stream { dry, timeout }`, `Shell`, `Live.deadline`). Its `testing` feature holds the tests' helpers (`apply_answer_for_test`, `writer_answered`, `render_to_string`…). The server's side: `crates/sentry-server/src/tui/target.rs` (`ServerTarget`, its `Own` effects, `testing::{srv, wf, data_ev}`) + `target/upkeep.rs`; `tui::target(remote)` is what `App::new`/`App::add` build it with (`tui::app(remote, tx)`: the server alone, the tests'). This machine's side: `crates/sentry-local/src/tui/target.rs` (`LocalTarget`: the store, the schedule, `lift` turns the screens' `tui/app.rs` `Effect`s into the app's or sends them back as `Effect::Own` → `on_local`; reboot, `run_go`, rollback, baseline edits) + `target/upkeep.rs` (lists, Claude's profiles and requests, the workflow plans' box and keys); `tui::target(cfg)` likewise (`tui::app(tx)`: alone); `tui/app.rs` is only the screens' effect types and the tests' `App` wrapper (`for_test`, `*_for_test`).
- A scope (`maint::root`, `maint::data_root`, the ring, baseline): `""` this machine, a plain name `servers/<name>`, `net:<name>` `networks/<name>`; `maint::label` drops the prefix. Never build those paths by hand.
- Test support in core is behind its `testing` feature, enabled only through the other crates' dev-dependencies (scratch XDG dirs, `claude::TEST_AVAILABLE`). Fixtures stay in the root `tests/fixtures/` (`../../tests/fixtures` from a crate).

## Commands
- Build/test: `make check` (= `cargo build --release && cargo test && cargo clippy --all-targets -- -D warnings && cargo fmt --check`)
- Snapshot tests: `cargo insta review` (or `INSTA_UPDATE=always cargo test` and then inspect `git diff`)
- Tests run with `TZ=UTC` (`.cargo/config.toml`), so snapshots match CI; `cargo run` shows UTC times too unless `TZ` is set.
- Unit tests never touch the real config/data/cache: `paths::xdg` gives each test process a scratch root under the temp dir (XDG_* ignored). Live tests (`#[ignore]`) call `crate::paths::use_real_dirs()` first, which honours XDG_* again; a new live test must too.
- CI (`.github/workflows/ci.yml`) runs `make check` plus MSRV (1.95, set by sysinfo) and a privacy scan on every PR. Never push to `main`: branch, PR, the user merges.
- Re-capture fixtures: `scripts/capture-fixtures.sh` (scrubs the username and IPs; journal fixtures are synthetic, never captured)
- Install: `make install-binary` (copies `target/release/sentry` to `~/.local/bin/sentry` and links `sentry-server` and `sentry-network` to it; `uninstall-binary` removes all three)
- Try a collector: `cargo run -q --bin sentry -- collect ostree`; a job plan: `cargo run -q --bin sentry -- job cleanup-flatpak --dry-run` (one binary; the server's commands: `cargo run -q --bin sentry -- server collect <name> probe`; the network's: `cargo run -q --bin sentry -- network collect probe`)
- Manual TUI tests: point `XDG_DATA_HOME`/`XDG_CONFIG_HOME` at a scratch dir so reports, the log, tasks.toml and baseline.toml stay out of the real ones

## Notes
- `XDG_CACHE_HOME` may be set (some dev shells set it): caches then live there, not `~/.cache/sentry`.
- Render tests: `crates/sentry-local/src/tui/screens/tests.rs` builds a `DataStore` from fixtures; snapshots in `crates/sentry-local/src/tui/screens/snapshots/`. The store's `tasks`/`maint_log`/`plans`/`snoozes` exist only in tests: `App::for_test` moves them into the slot's `Shared`, where the app keeps a target's records; screens read those through `View.sh`.
- `assets/workflows/*.toml` are embedded and seeded to `~/.config/sentry/workflows/` when missing; `release-rebase` is `draft = true` (no rebase has been run end to end).
- Workflow tests: put a harmless TOML in a scratch `XDG_CONFIG_HOME`, run with `SENTRY_NO_REBOOT=1`, fake a reboot by editing `boot_id` in `state.json`. A unit test that starts a run for real (the scratch data dir holds one at a time) takes `runs_turn()` first (`crates/sentry-local/src/tui/screens/tests.rs`; the server's `startable`; the window's `local_wf`), and ticks only its own rows: the updates row is the real quick-update.
- Screens: `1` Dashboard, `2` Processes, `3` Network, `4` Containers, `5` Flatpaks, `6` Maintenance, `7` Cleanup, `0` Upgrade, `H` History. Maintenance (`crates/sentry-local/src/tui/screens/maint.rs`) ranks `crates/sentry-local/src/maint/local.rs` (pure) recommendations (both engines end in `maint::rec::finish`: tasks due join, a task and a rule on the same `Target` become one row, snoozes drop, rank by level; both draw and hint through `tui::maintlist`, whose `Verbs` say which keys a row takes): findings, updates (Enter = `quick-update`, the one apply path; the TUI never offers `update-apply`), a staged reboot, tasks due (jobs' cadences are derived tasks: `jobs::state::tasks`; `tasks::effective` puts tasks.toml over them), failed jobs, cleanup, a run in progress, ready plans. Job runs, reboots, fixes and toolbox upgrades are `LogEntry::event`s in the log (`jobs.json`/`cadence.toml` are migrated once, `jobs::state::migrate`). The old Audit screen is a view inside it (`F`, `Maint::view`); Cleanup stayed a screen (the cleanup recommendation and `C` go there); `updates.rs` is only helpers (deployments panel, rollback, what's waiting). The cursor follows its row by key (`Maint::sync`); while that row is away (the updates' row is withheld during quick-update, and the run's own row comes in on top) it waits on the nearest row that was after it (`Maint.order`), else before, and goes back when the row does; a key on the list takes the row under the cursor (`take`). It used to adopt whatever sat at the old index: the first row, after a run.
- `crates/sentry-core/src/maint/` is shared by every target: the log + `LOG.md` ledger, plans, reviews (server `""` = this machine: `~/.config/sentry/{log,plans,reviews}/`; a server's under `servers/<name>/`), snoozes, `Level`, and `retention` (`[retention]` in config.toml, pruned at TUI start and after writes). Reviews are written by `docview::Writer`; local prompts in `crates/sentry-local/src/tui/plans.rs`. Plans are kept by apply sessions. Tasks (`crates/sentry-core/src/maint/tasks.rs`, `tasks.toml` beside the log): a review ends with a ` ```sentry-changes ` TOML block (`crates/sentry-core/src/maint/changes.rs`: add/remove/change a task, later/back, and on a server track/untrack/ignore/item; `take` validates against `Known` and drops with a reason) → `ReviewHead.changes`; the review window (`crates/sentry-core/src/tui/reviewview.rs`, `R`: brief → Enter starts → the changes ticked, Space unticks, Enter applies them together through `changes::settle`/`apply`, one `kind = "review"` log entry; no confirm box) is the same in every target (`review_open`/`review_start`/`review_apply`: `sentry-app`'s `slot/review.rs`); both rule engines turn due tasks into `task:<id>` rows (`Action::Task`); done is read from the log (the workflow/item change ended well; for `run <wf>` a task's `item` narrows it only when the run's entry names an item: a run that names none, the workflow as a whole, does it (`tasks::item_fits`), or `d` → `LogEntry::task`, tagged `task:<id>`). Enter on a by-hand task is an apply session (without Claude, its steps); `m` shows its steps and offers mark done. Tests use `App::for_test` (`win.offline`): nothing is written or sent.
- The frame (`crates/sentry-core/src/tui/frame.rs`, every target draws through it; `sentry-app`'s `Prompt` (`effect.rs`) is `WfVar`/`LogNote`/`LogAddNote`/`TaskEvery`/`TaskNote` and `Own` (a target's own: `Target::on_prompt`; sentry's workflow values), handled in `submit`/`cancelled` (`slot/core.rs`); `Ways.label` rewords one): `layout` (top bar, strip, rule, banner row, body, rule, key bar; under 80×24 a placeholder), `draw_top`/`draw_tabs`/`draw_banner`/`draw_keybar` (hints fitted, the toast at the right for `TOAST_FOR`), `help_modal`, `quit_modal`, `claude_choice`, `draw_run`/`run_key`, and `layer(&Open)`: the one order whatever is open gets keys and pastes and names the key bar's hints (Unlock → Run → Choice → Modal → Apply → Chat → Input → Docs → Screen; `Slot::open`; Unlock is the sudo password typed in the key bar). `tui/input.rs` is the one input line (`Input<P>`: filter, command, a `PromptLine`; Backspace on nothing closes a filter or command, never a prompt); `tui/modal.rs` has `Choice<E>`, `answer` (Enter/y, Esc/n/q) and `pick`. `ScreenId` (`tui/mod.rs`) is every screen any target has (`Svc` is the server's `5`, `Clients` the network's `2`, in no set yet); each declares a `ScreenSet` (`SCREENS` in its `tui/mod.rs`: strip order, aliases, `from_name` by slug, short name, alias or a 3-letter prefix) and `Keymap::new(&SCREENS, &cfg.keys)` binds only those (`[keys] screen.<slug>` of the other program's screen is skipped quietly). `Cursor` lives there too.
- One window, several targets (`crates/sentry/src/tui.rs`, `crates/sentry-app/src/app.rs`): `sentry` opens this machine plus a slot per server in `server_config.yaml` and per network in `network_config.yaml` (neither file: this machine alone); the Config tab is always the strip's last entry (the Config area, below); `sentry-server [name]` / `sentry-network [name]` the same window on that target (`tui::Open`, `plan_all`). `[targets] show = ["local", "srv:<name>", "net:<name>"]` (core `config::Targets::pick`) orders and hides them; a server or network asked for by name opens even when left out. The strip is in the top bar (`frame::Top.targets`, `TargetTab`, `Mark`; always there, since the Config tab is: one target is `F1 <it>  F2 config`; names cut, then keys only, when narrow): key, name, `*` at work, `!` needs you, `auto`. Keys are the window's (`Keymap::target`, never `resolve`): `F1`… by place, `{` / `}` round, the Config tab the last place (`[keys] target.<n>`, `target.next`, `target.prev`), taken before the slot except that a character is text where text is typed (`Slot::takes_text`: password, session, chat, input line); `:local`, `:server <name start>`, `:net <name start>` (`Ident.word`; `:net` alone is the Network screen of a target that has one, since a target's screen names come first; `Win.target_cmd`, after the target's own `:` commands and screen names). Each slot has its own keymap, screen set and input line: `Slot::park` swaps them with `Win.keys`/`Win.input`, so inside a flow `w.keys`/`w.input` are always that slot's (a prompt stays with the target that asked, text kept). A slot that never had the window is `asleep`: `App::start` only picks up its run left in progress (`Slot::pickup`); its records, first fetches and review at start come with its first focus (`Slot::shown` → `start`; later focuses → `enter(screen)`).
- Parallel across targets, one after another within one: every slot's events land in it whatever is in view (`App::with`), `App::tick` ticks every slot (run, session limits, timeouts), `next_due` asks every slot; only the slot in view polls for its screen (`Cx.focused`; out of view `Slot::enter` fetches nothing). A run goes on off screen `0` and out of view (no in-view rule; `Ways.auto_polled` is only whether the next auto step is also looked for on ticks). `Slot::needs(line)` → `Needs::{Nothing, Working, You(what)}` is the strip's mark; a slot out of view that comes to `You` is flagged and said once (`App::flag`: "<target> · needs you: <what>"), and never gets keys: its boxes, session window, prompts and password line are drawn and answered only in view (the password prompt names the target when there are several; `C-f` forgets the one in view). Toasts from a slot out of view carry its name (`Win.speaker`). Auto keeps answering out of view what `auto::answers` allows; the rest waits and flags. This machine's reboot ends the TUI (`Ways.reboot_ends_tui`): `wf_exec` holds it while another slot is `Working` (`Win.others_working`, `Slot.reboot_held`; the run's log and the banner say for whom) and `reboot_when_settled` sends it from `tick`. `q` with several targets lists what each has going (`App::quit_box`, `Slot::going`); shutdown is per slot as before. The terminal is handed over only for the slot in view (`App::handed`); the others' events queue. The locks (`runs_turn`, `startable`, one run per target's `runs` root) are per target. Tests: `crates/sentry/src/tests.rs` (`two_with(server, sudo_asks)`: this machine + a synthetic server per test, since runs are kept by name; `local_wf` serialises this machine's runs), `live_two_targets`.
- A resolved row leaves at once (every target; `crates/sentry-app/src/slot/rows.rs`): everything that can change the Maintenance rows ends in `Slot::rows_changed` (the records read again from disk, `Target::refresh(Why::Lists, sh, cx)`, `settle(Lists)`, Records' data replaced where it's open): a task done/removed/its cadence, `z`, expected and its undo, a review's changes, a run's or a session's log entry (`log_event`), a plan kept or closed, a re-audit. Don't reload one record and refresh by hand: call it. `Slot::look` finds what changed on disk without the app by comparing times (`Stamps`: the records' files and `Target::files()`, the target's config YAML / `items.toml` / `watch.toml`; a change of the target's own is `Why::Edited` first): on `r`, on `enter`, on focus (`shown` → `enter`), after Claude's turn and after an editor. No watcher. A stored report's `expected` flags are from when it was written: remote targets mark them again (`remote::audit::mark_expected`, `ServerTarget::remark` / `NetworkTarget::remark`) on every report that arrives and on `Why::Lists`, and drop findings about what isn't watched any more; this machine judges by `data.baseline` as drawn. Offline (tests) nothing is read or written: baseline edits are made in memory on all three. The matrix: `sentry_app::resolve` (`Way`, `Rig`, `run`, `check`; `Way::RunForItem`: a review's task with an item, done by a run that names none; no catch-all match, so a new way must be handled) → `every_way_a_row_is_resolved_updates_the_list_at_once` in each target's tests, `a_resolved_row_leaves_at_once_on_every_target` in the window's, and `crates/sentry/tests/rows_on_disk.rs` (a process of its own: the ways that write files every test of a process shares). `server_wf` in the window's tests refuses a server name used twice (runs are kept by name).
- The config files have one writer (core `crates/sentry-core/src/cfg/`): `ConfigFile` (implemented beside each type: core `Config`, sentry-server `ServerFile`, sentry-network `NetworkFile`: `FILE: FileId::{App, Servers, Networks}`, `FIELDS`, `parse`); `render` is the only way a file's text is made (a fixed header, YAML through serde-saphyr with `compact_list_indent: false`, TOML through `toml::to_string_pretty`; a setting goes when the value reads the same without it, `prune`, so the types carry no `skip_serializing_if`; refused unless it reads back equal); `save(path, text)` copies the file first to `<file>.bak-<UTC stamp>` (`-2`… within a second; newest `BACKUPS` = 5) then `write_atomic`; `update::<T>(path, f)` = load, change, save, returning `Saved { backup, handwritten, dropped }` (`lines()` for a terminal). Changes are by path on `cfg::Value` (an ordered tree, typed values through JSON both ways so the type validates): `Change { file, path (`servers."my.server".timers[2].max_age`), from, to, by: By::{You, Agent}, on }`, `diff` (lists aligned by LCS, a record's field is its own change) and `apply` (fails when `from` isn't what's there: a conflict, never an overwrite); `Doc<T> { path, on_disk, stamp, now }` (`load`, `changed_on_disk`, `pending`, `rebase` → made + conflicts, `save` refused when changed underneath). `handwritten(text, v)`: the text isn't what `render` makes of it (comments are lost on save; said). `Draft<T> { entry, notes: Vec<Note { path, text }> }`: both `init`s draft typed (`sentry_server::init::draft` → `Draft<Server>`, `sentry_network::init::draft` → `Draft<Network>`; what the text drafts' comments said are notes at their paths) and write through `init::write` → `cfg::update` (`sentry-server init --write` inserts into the parsed file; `sentry-network init` adds a network to a file that has others; a name there is refused; tests `the_typed_draft_is_what_the_text_draft_was` hold the old text drafts' output). Field tables (`cfg::fields`: `Field { path pattern (`*` a key, `[]` an index), label, help, kind, essential }`, `config::FIELDS` in each config module; `every_setting_has_its_field` in each checks a fully set value's every leaf against them, both ways). Lint at start (`crates/sentry/src/cfgcmd.rs` `read()`: every file's unknown keys, parse error, `lint`, `[keys]`, `[targets] show`; offline) → `Win.config_problems: Vec<sentry_app::cfgarea::Problem { file, entry, text }>` and one toast (`cfgarea::toast`: the first, how many, that the Config tab lists them). `sentry config check` (✓/✗ per file, exit 1), `show [app|servers|networks]` (what `render` makes of each; a network's MACs and hostnames are its salt's tags when it has one: `redact::Salt::existing`, `tag_identities`), `explain [<path>]` (`cfgcmd::explained`); `sentry config` alone opens the window on its Config tab (`tui::Open::Config`).
- The Config area (`crates/sentry-app/src/cfgarea/`: `mod.rs` state and staging, `kind.rs`, `keys.rs`, `draw.rs`, `save.rs`, `agent.rs`; design `docs/design/config.md`, its "As built" section says where the code went another way): part of the window, not a target. `App { config: ConfigArea, in_config }`: `focus` stays the slot index (the one in view, or the one that was before the tab took the window; its keymap and input line stay parked in `Win`), `in_config` says the area has the keys, pastes, frame and `:` line (`App::focus_config`, `config_at_start` for `sentry config`; `App::focus` leaves it). While it does, no slot is in view: `with_one` treats every slot as out of view (`Win.focused` false, toasts named, `flag`), `tick`/events/marks go on, a slot's command never gets the terminal (`take_suspend` is the area's editor then, `config_handed`). The strip (`App::strip`): the slots not `hidden`, then the Config tab, always last, its key the next by place (`Action::Target(n)`), `:config` (`app::CONFIG_WORD`; `Slot::command` hands it to `Win.target_cmd`); `config*` = something staged, `!` (`Mark::You`) = problems. Accent: `frame::TargetTab.accent` / `frame::Top.accent` / `frame::layout_ruled` (`cfgarea::accent` = `t.mag`): the chip `sentry config`, its tab when in view and the rule under its screens; tests read colours with `frame::text_on` / `text_in`. Its screens are its own enum (`cfgarea::Screen`: `1` Overview, `2` Agent, `3` This machine, `4` Servers, `5` Networks, `6` Window) drawn through `frame::draw_tab_items` (`TabItem`; `draw_tabs` maps `ScreenId`s onto it; `ScreenId` is untouched), badges = problems per screen, what is staged on Overview. **`Kind`** (`kind.rs`, registered in `crates/sentry/src/tui.rs` `kinds()` beside the target makers; `App.config.register`): `id`, `load(path)`, `fields`, `entries` (`Entry { name, kind, summary, target: the `[targets] show` id, screen }`), `sections(entry)` (`Section { title, items: Item { path, empty } }`: only `essential` fields), `entry_of(path)`, `problems(doc, warnings)`, `explain`; implemented by `sentry_local::cfgkind::AppKind` (config.toml: entries `cfgarea::{AGENT, MACHINE, WINDOW}`), `sentry_server::cfgkind::ServersKind`, `sentry_network::cfgkind::NetworksKind` (in full: see "Systems in the Config area"). ## Rules
- **No background processes**: no systemd units, timers or autostart. Threads die with the TUI. Two bounded exceptions, both remote and both ending by themselves: ssh's multiplex master (15 s, see sentry-server) and a router guard's dead-man (at most `guard.window`; its snapshot and one-shot boot hook sit on the router's flash for the same time; see sentry-network). One program is started and not waited for, and it isn't sentry's: the desktop's opener (`xdg-open`, `Cmd::detach`) on a SusCheck picture, by the user's `o`; it is the user's own viewer, and the cached picture it is given goes when the window closes.
- Every external command goes through `exec::Cmd` (`Cmd::host` for host userspace; `Cmd::bytes_to` hands a command's stdout to a `Write` as raw bytes, for a binary stream). Never call `std::process::Command` directly. Dev happens in a toolbox, where `Cmd::host` adds the `flatpak-spawn --host` prefix.
- Host `/etc` is read via `paths::host_root()`.
- Collectors: a pure `parse()` (fixture-tested) and a `collect()` (exec + parse). A missing binary is `CollectError::Unavailable`, never a panic.
- Slow or network collectors run only on `c`/`r` and are cached (`cache.rs`). Nothing refreshes unless its screen is visible.
- Destructive actions: preview → confirm modal → streamed output.
- Never run `rpm-ostree upgrade/rollback/rebase`, `systemctl reboot`, or podman rm/stop for real while developing.

## sentry-server (`crates/sentry-server/src/`, `crates/sentry-server/src/main.rs`)
- A second kind of target (a library; `sentry-server …` is the one program under that name): monitors a server over ssh (`exec::Cmd::ssh`; its `remote::Remote` wraps `sentry_app::remote::Remote` with `cfg` and `inventory` and derefs to it; `workflow.rs` keeps `cond`, `RemoteEnv`, `BUILTINS`, `SEEDS`, `resume`/`begin`; `audit.rs` `derive`/`run`; `gateway.rs` `READ_ONLY`/`allowed`/`runnable`), configured by `~/.config/sentry/server_config.yaml` (sample: `assets/server_config.example.yaml`; written only through `cfg`: `init --write`).

## sentry-network (`crates/sentry-network/src/`)
- A third kind of target (a library; `sentry-network …` is the one program under that name, `crates/sentry/src/network.rs`): a home network through its router, OpenWrt over ssh as root. `remote::Router` wraps `sentry_app::remote::Remote` (`Privilege::Root`, scope `net:<name>`, `.dropbear()`) with its `cfg` and derefs to it. Built so far: the config, the collectors, the audit, Dashboard, Clients (`2`), Network (`3`), Security (`4`: the list, its actions, the family filter), Maintenance (`6`: findings, tasks, the Items firmware / packages / backup), Upgrade (`0`: its workflows) and History, encrypted config backups, the recorder, the CLI, the policy and gateways, scrubbing, Claude (`tui/ask.rs`), the guard, and the workflows that change a router (`package-update`, `guarded-change`, `firmware-upgrade`). `firmware-upgrade` has been run end to end on one real router once (a patch release within its series: check, backup, plan, download, flash, restart, return); a move to another series is refused by its plan and has never run. Not run end to end on a real router: a guarded Wi-Fi change on a router with radios.
- **The repo is public: nothing about the developer's real network goes into git** (the router's ssh alias and hostname, SSIDs, addresses, MACs, device names, the ISP), nor into commit messages. Naming a router model as an example of a supported device is fine. Fixtures in `tests/fixtures/network/` are synthetic (real formats, invented content: `home`, `myrouter`, `Example Router AX`, 192.0.2.x / 198.51.100.x / 203.0.113.x, 2001:db8::, MACs 02:00:5e:00:53:xx). Captures from the real router, and the notes on what its busybox can and can't do, are only in the gitignored `tests/fixtures/network/local/` (`NOTES.md`: read it before writing a collector).
- Against the real router only reads while developing: what the collectors run, `sentry-network check|collect|audit|init|backup` with scratch `XDG_*` dirs (a backup made there is the real config, Wi-Fi passphrase and keys included: a throwaway key, and delete it and the backups afterwards), and the `#[ignore]` live tests. Never `uci set/commit`, a restart, `apk add/del/upgrade/fix`, `owut`, `sysupgrade` (but `-l` and `--create-backup -`), a reboot, a guard past its preflight (no arming, no `/tmp/sentry-guard-*`). Everything that changes a router is developed and proven against the disposable one (`scripts/live-router.sh`). `apk update` only as the user's `r` on Maintenance (and `live_refresh_index`, which needs `SENTRY_NETWORK_REFRESH=1`): it writes the tmpfs index cache, nothing on flash.
- Dropbear: `ssh -tt` with the local stdin at its end (what `Cmd::stream` does for a server) prints nothing and fails there. `Cmd::hold_stdin()` (set on every command a `Remote::dropbear()` builds) makes `stream` keep a stdin pipe open, unwritten, until the command exits (`Cmd::streamed`: the terminal, and whether stdin is held); stopping the local ssh still ends the remote command (`live_dropbear_stream` in `sentry-app`: gone within the first 250 ms check). Captured commands (`output`) and every other host are untouched. No `nohup`, `timeout`, `sudo`, `ss`, `jq`, `openssl`, `base64`, `curl` on the router, `ps` has no `-o`/`-e`, and busybox `sleep` takes whole seconds.
- Config (`config.rs`): `~/.config/sentry/network_config.yaml` (sample `assets/network_config.example.yaml`), `networks: <name>: { router: { ssh, kind: openwrt }, expect: { zones, forwards, listeners }, devices, thresholds, backup, maintenance: { items, cadence }, notes, claude }`. The whole shape is parsed and linted now (`lint`: names, forwards' proto/port/address, `proto:port@zone` listeners against the zones, MACs via `config::mac`, a `private_mac` device known by hostname, age/ssh recipients, ids and cadences), `guard: { window }` (5–3600 s, default 300) included. `backup.recipients` are checked by `backup::recipient` (a real age key, or a file of them; an ssh key is refused). `Ports` is one port or a range; `local_mac` is the locally-administered bit. sentry writes it only through `cfg` (`init` adds a network: `init::write`).

- **Policy** (`policy.rs`, pure; `classify(line) -> Class`, `verdict` with why and, for a read, `run`; `verdict_argv` for `exec`'s words; `refuses`): root has no sudo line, so every line Claude sends is read before any connection. `Read < Change < Guarded < WorkflowOnly < Never`. **`Read` is decided positively and rebuilt** (`read.rs`, `read::plan`): a line is a read only when it parses under the grammar there, and then the router's shell never sees the line as written, only what sentry made from the parse. The grammar: simple commands joined by `|`, `;`, `&&`, `||`; a program on `read::PROGRAMS` (by name: never a path, `busybox x`, `env x`, a quoted-apart name is still the list's) with literal arguments its `rule` allows flag by flag (`getopt`: clusters taken apart, flags before operands, no operand starting with `-`); only `2>&1`, `2>/dev/null`, `>/dev/null`; single quotes and plain double quotes group. Outside it: `$`, backticks, backslashes, `#`, `~`, braces, parentheses, `<`, `&`, an assignment, a line break or control character, `$`/backtick/backslash in double quotes. A `*`/`?` outside quotes is a pattern only in a path under `read::GLOB_DIRS` (/sys/class/net, thermal, hwmon, ieee80211, /sys/devices/system/cpu, /proc/net, /proc/sys/net; no component starting with `.`, since ash's `.?` matches `..`), sent bare; anywhere else it puts the line outside (quote it to mean the characters); an unquoted `[0]` is literal for uci and grep. Paths are made plain first (`read::normal`: `//`, `/./`, `..` by its text; climbing above `/` or a relative path is outside) and the plain path is what is checked and sent. Files are printed only from `READ_FILES`/`READ_DIRS` (named /proc files, /proc/net, /proc/sys, /proc/<pid>/{stat,status,statm,comm}, a few /sys/class dirs, the lease files, a few of /etc): not /proc or /sys as a whole, never /rom/etc, /overlay/upper/etc, /proc/<pid>/root, /proc/self, /dev. **Only the first command of a pipeline runs on the router** (`Source::Remote`, one `prog 'arg' …` line each, every argument single-quoted here): the filters (`read::FILTERS`: grep/egrep/fgrep without `-o`/`-r`/`-f`, head/tail by lines, sort without `-o`, uniq, wc, cut) and a filter's own file (`grep x /tmp/dhcp.leases` = `cat` there, grep here) are done on this machine **after the scrubbing** (`filter.rs`, the `regex` crate; `grep` basic/extended/fixed translated): a pattern matched on the router is an oracle for what the scrubbing hides (`grep -c "key='a"`). For the same reason no program selects by pattern or address there: `logread -e` is a grep here, `ip … show` takes `dev <name>`/`default`/`table`/`up`, no `ip route get`, `pgrep` by name without `-f`, no `iw … scan [dump]` or `station get`. `echo`, `true`, `false`, `sleep` (≤ 30) are done here. Not on the list (so a request, never a read): awk, sed, tr, od, hexdump, strings, xargs, sh, env, `sysupgrade -l` (sentry's own, one at a time: `Never` through the gateway), `route`, `ifconfig`, `arp`, `top` but `-b -n 1`. Invariant test (`read/tests.rs` `whatever_is_a_read_sends_only_what_was_understood`): 150 000 generated lines of shell metacharacters with allowed and dangerous commands; whenever the class is `Read`, every line sent parses under an independent reference tokenizer into exactly the one simple command the classifier saw. **Everything else** is read by the older conservative lexer (`verdict_at`, now only choosing among the classes that don't run by themselves): a line is its worst part (`;`, `&&`, `|`, newlines, `$(…)`, backticks, `sh -c`, `eval`, `xargs`, every `find -exec`, a heredoc's body, redirections), an unknown program's arguments are read as commands of their own (`wrapped`), and a line the grammar can't take apart is also read word by word with every shell character a break (`by_words`: a `reboot`, `uci commit` or secret path in a quote, a comment or `$'…'` still decides). Paths are squashed first (`//`, `/./`). What is left is `Change`, shown as it will run. `Guarded`: `uci commit`, staging verbs on `GUARDED` configs, init verbs on `GUARDED_SERVICES`, `wifi`, `ifup`/`ifdown`, `fw4 reload`, nft with any flag but `-a -n -s -j -t -y` or a changing verb, ip/iw/brctl/route changes, `ifconfig` beyond one interface, `arp` beyond `-n`/`-a`. `WorkflowOnly`: `sysupgrade` (flash), `owut upgrade|install|download`, `apk upgrade`, `apk fix`, `apk add` of a base package or with `-u`, `reboot`/`poweroff`/`halt`. `Never`: `secret_path` (shadow, dropbear's keys, `/etc/config/*` raw, hostapd's files, flash and memory devices, `/proc/<pid>/{environ,root,cwd,fd,mem}`, `/sys/kernel/debug`, `/tmp/.uci`, anything named `sentry-guard`, `..`), `sysupgrade -b|-l`, `passwd`, `dropbearkey`, `firstboot`, `mtd`, `dd` to a device, `rm`/`find -delete` from the top, fetch-and-run, a write under /etc, /usr, /lib, /bin, /sbin, /overlay, /rom, /dev, /proc, /sys (`sort -uo/etc/x` too: the target follows the `o` in its cluster), `sysctl -w`, `kill` by number / `pkill -f` / a signal to a daemon the network is reached through or part of its name (`DOORS`), `apk del` of a base package or with `-r`, starting a listener (`telnetd`, `dropbear`, `uhttpd`, `nc -l|-e`, socat…), `tc`/`rmmod`/`insmod`/`ethtool -s`/`hostapd_cli`/`wpa_cli` and the like, any `uci` write to `rpcd`/`ucitrack`/`luci`, and a `uci` line that sets **an option that is a script run as root or a file a daemon reads, writes or serves** (`policy::runs_or_reads`, also refused in a guard line: firewall includes and `path`/`type`, dnsmasq `dhcpscript`/`*file`/`confdir`/`tftp_root`/`enable_tftp`, odhcpd `leasetrigger`, uhttpd `interpreter`/`*_prefix`/`home`/`cert`/`key`, dropbear `BannerFile`/`*keyfile`, `pppd_options`, `hostapd_options`, anything with `script`/`hook`/`command`/`handler`/`plugin`, ending in `file` or `_options`; the names are OpenWrt's from memory, not read from its docs).

- Backups (`backup.rs`; `sentry-network backup [name] [--verify]`, `backup list|key|decrypt`): the `age` crate (0.12, no features: x25519 recipients only), no external binary. `run`: recipients (none → `Error::Unavailable`, exit 3), release, `digest` (`sysupgrade -l | xargs sha256sum` → `Manifest`, each hash a `Salt::tag` as it's parsed), `uci`, then `create`: `Cmd::bytes_to` (core: raw stdout chunks to a `Write`, nothing decoded or kept) writes ssh's `sysupgrade --create-backup -` into `Plain` (counts, checks the gzip magic) → the age `StreamWriter` → a `.…tmp` file (0600, in the 0700 dir) → `rename`; any failure drops the temp file (`Temp`). Then the sidecars `<stamp>.manifest` (`<tag>  <path>`) and `<stamp>.uci` (`pkg.section.option=value`, secrets already tags), then `prune_dir` (`backup.keep` newest + each month's first for a year, sidecars with them). `status_in` = newest vs a fresh digest (`Changed { files, options }`; `diff` names a secret option without its value). `verify` (the workflow's second step): an age file, not empty, its manifest equal to a fresh digest. The archive holds one file `sysupgrade -l` doesn't list (`etc/uci-defaults/10_disable_services`, which sysupgrade writes straight into the tar stream). **One `sysupgrade` at a time:** it keeps its file list at a fixed `/tmp/sysupgrade.conffiles` on the router, so two at once (the screen's digest while a workflow step verifies, the audit beside a backup being made) give a digest with files that aren't there, or an archive from half a list. `backup::turn(scope)` is an exclusive `File::lock` on `<data>/networks/<name>/sysupgrade.lock` on this machine, held by `digest` and across `run`'s digest and stream (threads and the steps' own processes alike; found by `live_backup_workflow`, which fails without it). Someone else's sysupgrade (LuCI's backup button at that moment) isn't covered. Measured on the real router: the archive 0.8 s (37 files, 10 KiB), the digest 0.16 s.
- Workflows (`workflow.rs`, `assets/network-workflows/`, seeded to `~/.config/sentry/network-workflows/`; a network's own in `networks/<name>/workflows/` replace them): the shared `remote::workflow::Session` with `RouterEnv` (built-in `network`; conditions `guard_waiting`, `packages_leaf` (one `apk upgrade --simulate` on the router when the step is reached); the boot id is read only for a workflow that has a reboot step), `Session::on(WORDS)` ("the router"), `PROG = "sentry-network"`: a step starting with that runs here with the network's name after its first word (`sentry-network backup --verify` → `sentry network backup <name> --verify`). `Host::{workflows, begin_run, resume_run, run_go (root: no sudo), step_ended (reads the backups again)}`. Screen `0` is `sentry_app::remote::wfview` (the server's Upgrade screen made shareable: `Shown` carries the words; the server still draws its own copy). `config-backup`: both steps `gate = "auto"` and run here, so Enter on its row (the cadence's task, the unsaved finding, the backup item) is the only key, and in a series or with auto on nothing is asked. `package-update` (`cli::packages`, `packages.rs`): preview (`apk update` + list, auto) → backup (auto) → `plan` (auto: `apk upgrade --simulate <names>`, which writes nothing, parsed by `packages::transaction` and shown whole: apk takes along what the names depend on) → `upgrade` (confirm; `when = packages_leaf`: every package of the transaction is a `leaf_package`: `luci-app-*`, `luci-i18n-*`, `luci-theme-*`, `zoneinfo-*`, tcpdump, nano, htop, iperf, mtr, bind-dig, less, terminfo, owut; auto may confirm) or `upgrade-base` (confirm, `risky`: anything else, base system or not; never auto) → services + audit (auto). Both upgrade steps simulate again and the plain one refuses a transaction with a non-leaf (exit 3); an empty or unreadable simulation is never a yes; never a bare `apk upgrade`. `base_package` (the list a router doesn't boot or answer without, incl. ucode, libnl-tiny, libblobmsg-json, jsonfilter, ppp, uhttpd, firmware) marks rows and decides `apk add|del` in the policy. `guarded-change`: show (auto) → guard (confirm; never auto) → keep (confirm, `risky`, `when = guard_waiting`). `firmware-upgrade` (run end to end once on a real router, so no longer a draft; see Upkeep for how it starts) is `firmware.rs` (`sentry-network firmware <name> <step>`, every step here; the run's record across steps `networks/<name>/firmware.json`, `firmware::State`): `check` (auto: a release, same-series upstream look, a backup recipient, no guard pending or held, `owut` there, free memory ≥ `MIN_AVAILABLE`/`MIN_TMP`) → `backup` (auto: `backup::run` + `verify`, its name and time kept for the lost-contact words) → `plan` (auto: `owut check --verbose` → `parse_check` → `stops`: every `WARNING:`/`ERROR:` (`Warn`, each with plain words), missing/downgraded/failing packages, owut's reading ≠ the board's, another series (refused: patch releases only), nothing newer, no "safe" verdict; nothing newer and nothing else wrong is no failure: `plan_exit` → exit `NOTHING_NEEDED` (10), and the run ends done, the rest of its steps skipped as `workflows::NOT_NEEDED` (`remote::workflow::Session::nothing_needed`, taken only from a step of the program's own; works with any copy of the TOML), so starting it again on the newest release is no failed step handed to Claude; `upgrade_in` doesn't count such a run; `HARMLESS` is the short list that doesn't stop it: a default provided by another package, build failures of packages not installed here; the top-level packages by `rpc-sys packagelist` (owut's own source of names: no ABI suffix, unlike `/etc/apk/world`)) → `download` (confirm, `auto::never`: `owut download -V <planned> -i /tmp/sentry-firmware.bin`, with `backup::turn` held since it runs `sysupgrade --test`; then sentry's own: the image's sha256 and size against the server's manifest (`image_problems`), the version, every top-level package in the manifest, its own `sysupgrade --test` (from `/sbin/sysupgrade`: validates, writes only `/tmp/sysupgrade.meta`, exits before any flashing), memory left ≥ image + `HEADROOM`; any failure removes the files) → `flash` (confirm, `risky`, `auto::never`, the step's `ask` box: what happens, how long, what is kept, that nothing automatic rescues a failed flash; `backup::turn` held, then `no_guard` (no guarded change waiting, and `guard::turn` held, try-only so the two locks never wait on each other: no Security action or family filter is armed across a flash); the image's sum checked again; boot id, top-level packages, running services, leases and WAN noted; `flash_line`: `setsid sh -c 'exec owut install -i …'` apart from the session; watches it over new connections (`look`/`LOOK_SCRIPT`: boot id, `pgrep -x owut|sysupgrade|upgraded`, `FLASH_LOG`) for `WATCH` (180 s): a new boot, or two failed connections 3 s apart (one alone is a blip), or owut ended, hand over to `wait`; its ERROR lines are "nothing was flashed"; the box's line `workflow::DRAFT_LINE` "sentry has never flashed a router before this run." is only in a draft's copy and goes with `undraft`) → `wait` (auto: a `look` every 5 s, `poll` with `idle_for` (how long the old boot has answered with nothing of the flash running) tells apart `Back` (new boot), `StillFlashing`, `NotFlashed` (old boot, idle 20 s with no "Installing" line, 120 s after it, or at the deadline: `not_flashed_words`, the image removed, `flashed_at` cleared, exit `NOT_FLASHED`; never the lost-contact text), `Gone` (no answer at the deadline: `lost_words`, exit 1), `Stuck` (still at work on the old boot at the deadline); `WAIT` = 15 min from the flash (`deadline`; once past, `GRACE` 60 s); `SENTRY_FIRMWARE_WAIT`/`SENTRY_FIRMWARE_WATCH` are read only in a debug build (`knob`); a line every 30 s with the time since; `on_fail = manual`; `NetworkTarget::resume_run` retries a failed `wait` while `flashed_at` is set, so a window opened later carries on) → `after` (auto: the version is the planned one, `missing_after` (owut's replacements counted), the services that ran before (`services_lost`), WAN as before, leases back when there were some, where blocks.toml notes filtered devices the family filter read back (`family_after`: one line, in place for N devices or which aren't whole; said, never failing the step), the audit, a fresh verified backup; a done run makes the security audit's task due again, `secaudit::upgrade_in`) → `add-missing` (confirm, `risky`, `when = firmware_missing`: `apk update && apk add` exactly those names, `plain_name`) and `forget` (rollback: the image out of memory). A confirm step's `ask` (core `workflows::Step.ask`, any target's file) is a box `remote::wfview` shows on its Enter, in paragraphs, whose Enter runs it (only the network draws it so far). A step's text after ` -- ` is one argument (`Session::go`).
- Recorder: the ring is `<data>/networks/<name>/metrics/ring.bin` (the shared `remote::recorder`, 10 s / 72 h). The TUI feeds it from the Dashboard's probes (`record_sample`: CPU, memory, load, the uplink's bytes/s, the temperature, the overlay's share as the disk; not when `offline`, not while a recorder is live); `sentry-network record [name]` is the foreground loop (the shared `/proc` probe every 10 s, `ubus call system info` and the thermal zone once a minute).
- CLI (`cli.rs`, `init.rs`; `sentry-network [name]` opens the window on that network): `check [name]` (reachable as root, the tools there, release and board, the probe, ports, WAN, then each other collector with its time; exit 1 if something needed is missing), `audit [name]` (findings, the report's path), `collect [kind] [name]` (JSON; every kind without one, `updates` among them; `{"unavailable": …}` and exit 3 as `sentry collect`), `backup …` (above), `lint [name]` (offline), `record [name]`, `init <ssh> [--name N]` (one exec: the ifaces script, `uci show firewall`, `/tmp/dhcp.leases`; `init::draft` is pure and typed (`Draft<Network>`): zones and DNAT redirects as `expect`, each lease as an unnamed device, by MAC or, for a locally administered MAC, by hostname; the board, the ports and what wasn't taken as notes; added to `network_config.yaml` through `cfg` (made when it isn't there), a name already there printed with exit 1).
- The disposable router: `scripts/live-router.sh up|test [names]|sh|down` (`SENTRY_ROUTER_LABEL=<word>` in front: a second one beside one already up; podman, `openwrt/rootfs` 25.12.5 with procd, ubus, netifd, dropbear on a random localhost port, a throwaway key, a synthetic `/etc/config`; removes only what it made). Its tests (`live_router.rs`, `#[ignore]`, `SENTRY_ROUTER_SCRATCH=<name>` + `SENTRY_SSH_CONFIG` + scratch XDG, all set by the script): `live_router_policy` (reads rebuilt and scrubbed, the gateway's trace says what was sent; a grep's pattern never reaches the router; every review input refused with a canary untouched and nothing sent; run directly, ash 1.37 does read `$'…'` and `#` comments, and this busybox's `sort -uo<file>` exits 0 and writes nothing: its `-o` isn't built in), `live_guard_keeps`, `live_guard_reverts` (ssh moved to an unreachable port, window 8 s: configs back byte for byte, the logger line, the journal), `live_guard_wifi_asks` (waits; a base package and a non-leaf refused by the plain step; a leaf upgraded for real), `live_router_session` (`Win.scripted_turns`: the test gives Claude's answers, everything else runs: a guarded line in a plan sent back, then a plan with a `run` step and a `guarded-change` step approved, Enter on the guard step, kept, verdict, both log entries), `live_security_filter` and `live_security_takeover` (see the family filter), `live_firmware_upgrade` (the window, against the script's firmware stand-ins (`stubs`: `/usr/bin/owut` printing `tests/fixtures/network/firmware/`, a random 1 MiB image with a real sum and a manifest of what rpc-sys lists; `/sbin/sysupgrade` real but for `--test` and the flash; the pretend restart stops dropbear, removes the image, changes the boot id (the container's `boot_id` is a file of the script's bind-mounted over `/proc/sys/kernel/random/boot_id`), says 25.12.6, comes back after 8 s or 45 s; mode in `/etc/sentry-stub/mode`): a warning stops the plan, `newest` (owut says nothing newer: the run ends done after its plan, nothing downloaded, nothing handed to Claude), a wrong checksum stops before the flash and leaves nothing, not back by the deadline then a new window carrying on to done (no draft offer: it isn't one), a package missing then installed by `add-missing`; `silent`: owut ends without flashing or an ERROR line, said as not flashed within a minute and startable again; `hang`: owut at work past the watch, the wait says so and never that the router is gone).
