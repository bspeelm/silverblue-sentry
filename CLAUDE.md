# sentry: Silverblue monitor & maintenance TUI (Rust + ratatui)

Spec: `docs/spec.md`. Binding amendments: `docs/spec-addendum.md` (read both before changing behavior).
Design for M3–M7: `docs/design/m3-m7.md`.
Visual target: `docs/design/sentry-tui.dc.html` (read the source; don't render it).
Upgrade procedures: the user's personal notes in `docs/cheatsheets/` (gitignored, never commit or publish them) are the source for `assets/workflows/*.toml`.

## Layout
- Cargo workspace, one repo: `crates/sentry-core` (shared: exec, paths, config, baseline, finding, claude, maint records, workflow format + runner, disk/gpu/journal/net/procfs parsers, the TUI kit incl. the frame, chat, docview, maintlist, records), `crates/sentry-app` (what targets share beyond the kit: the app itself, below, and `remote/`: a host over ssh), the targets `crates/sentry-local` (this machine), `crates/sentry-server` and `crates/sentry-network` (libraries, each with a `testing` feature for the window's tests), and `crates/sentry`, the one binary (`main.rs` this machine's commands, `server.rs` the server's, `network.rs` the network's, `tui.rs` the window, `tests.rs` the targets side by side). Core never depends on the others; `sentry-app` depends only on core; targets never depend on each other; only `crates/sentry` depends on all three.
- One program, three names: called as `sentry-server` or `sentry-network` (argv[0]: the symlinks `make install-binary` makes beside it) or as `sentry server …` / `sentry network …` it is that command line (`main.rs` `as_command`), same output. A workflow step that runs `sentry-server cond …` finds it beside the program (`remote::workflow::exe`: `sentry server`); Claude's profiles call `sentry-server run|exec` from PATH (the symlink).
- `sentry-local` re-exports core under the old names (`crate::exec`, `crate::maint::log`, …); its `maint`, `workflows`, `collectors`, `tui` modules glob-re-export core's and add their own. sentry-server uses `sentry_core::…` explicitly (its own `config`/`maint`/`tui`/`audit` would clash).
- `crates/sentry-app/src/remote/` (moved out of sentry-server, which re-exports them under its old paths): `mod.rs` `Remote { name, host, scope, privilege, hold_stdin }` (`Privilege::Sudo { allow }`: `sudo -n` through the allowlist; `Privilege::Root`: bare argv, `sudo_mode()` is `SudoMode::Root` without an exec; `Remote::dropbear()` sets `hold_stdin`, see sentry-network), `Error` (the server's `SrvError`), `host`; `workflow.rs` (`Session` with a `Box<dyn Env>` and the program's name, `Session::on(Words)` for what it calls its host (default "the server"), `Exec`, `Live`, `tee_to`, `no_prompt`, `root`/`own_dir`/`pick_dir`); `probe.rs`; `recorder.rs` (`record(r, extras)`); `audit.rs` (`Report<S>`, the report store, `set_expected*`, `pattern_for(ns, …)`, `listener_status`/`listener_id`); `gateway.rs` (`SECRET`, `Held`, `words`/`commands`, `run_cli(prog, r, line, policy)`, the read queue); `upstream.rs` (GitHub, endoflife.date, `comparable`); `wfview.rs` (screen `0` for a host whose runs are `Session`s: the list, the run, its card, in the run's own words; sentry-network uses it).
- `crates/sentry-app/src/` is the app (`sentry_app::App`, a slot per target): `target.rs` (`Target` with `Upkeep`/`Asks`/`Host`, object-safe: a target owns its fetch threads, kinds, store and screens; `Ident` its names and words; `Ways` where a program's flows go their own way: words and rules such as `auto_polled` and `reboot_ends_tui`, default = the server's, each flow asks `self.ways`; `Cx` what it may look at, incl. `at`, the one clock (`Win.at`, the event's instant), and `focused` (the target has the window: only then may `due`/`next_due` poll for its screen); `Mail` how its threads and streams answer, tagged with its id; hooks with a default for what only one program does: `on_prompt`, `pane_ended`, `plan_key`, `plan_written`, `chat_continue`, `wf_start`, `session_starts`, `run_cmd`, `run_plan`/`run_info`, `find_workflow`), `app.rs` (`App { slots, focus, win }`, `App::new` + `App::add`; `Win`: theme, keymap, toast, the input line, the help/quit box; `Event` carries a target id; `App::with(i, …)` runs a slot's flow with the window as that slot sees it), `slot.rs` + `slot/` (`Slot`: one target, its `Shared` records, the screen in view, run, session, series, chat, writer, Records, its boxes; every flow is an `impl Slot` method taking `&mut Win`: `core` events/keys/`open()`/prompts, `effects`, `session`, `wf`, `series`, `review`, `records`, `draw`), `shared.rs`, `effect.rs` (`Effect`, `Prompt`, `WfCmd`; a target's own effects travel as `Effect::Own` and come back in `Target::on_own`/`after_suspend`), `run.rs` (`WfRun`: a workflow run as the app sees it; `remote::workflow::Session` is one, sentry's `tui/wf.rs` `Session` the other; `Exec::Stream { dry, timeout }`, `Shell`, `Live.deadline`). Its `testing` feature holds the tests' helpers (`apply_answer_for_test`, `writer_answered`, `render_to_string`…). The server's side: `crates/sentry-server/src/tui/target.rs` (`ServerTarget`, its `Own` effects, `testing::{srv, wf, data_ev}`) + `target/upkeep.rs`; `tui::target(remote)` is what `App::new`/`App::add` build it with (`tui::app(remote, tx)`: the server alone, the tests'). This machine's side: `crates/sentry-local/src/tui/target.rs` (`LocalTarget`: the store, the schedule, `lift` turns the screens' `tui/app.rs` `Effect`s into the app's or sends them back as `Effect::Own` → `on_local`; reboot, `run_go`, rollback, baseline edits) + `target/upkeep.rs` (lists, Claude's profiles and requests, the workflow plans' box and keys); `tui::target(cfg)` likewise (`tui::app(tx)`: alone); `tui/app.rs` is only the screens' effect types and the tests' `App` wrapper (`for_test`, `*_for_test`).
- A scope (`maint::root`, `maint::data_root`, the ring, baseline): `""` this machine, a plain name `servers/<name>`, `net:<name>` `networks/<name>`; `maint::label` drops the prefix. Never build those paths by hand.
- Test support in core is behind its `testing` feature, enabled only through the other crates' dev-dependencies (scratch XDG dirs, `claude::TEST_AVAILABLE`). Fixtures stay in the root `tests/fixtures/` (`../../tests/fixtures` from a crate).

## Commands
- Build/test: `make check` (= `cargo build --release && cargo test && cargo clippy --all-targets -- -D warnings && cargo fmt --check`)
- Snapshot tests: `cargo insta review` (or `INSTA_UPDATE=always cargo test` and then inspect `git diff`)
- Tests run with `TZ=UTC` (`.cargo/config.toml`), so snapshots match CI; `cargo run` shows UTC times too unless `TZ` is set.
- Unit tests never touch the real config/data/cache: `paths::xdg` gives each test process a scratch root under the temp dir (XDG_* ignored). Live tests (`#[ignore]`) call `crate::paths::use_real_dirs()` first, which honours XDG_* again; a new live test must too.
- CI (`.github/workflows/ci.yml`) runs `make check` plus MSRV (1.95, set by sysinfo) and a privacy scan on every PR. Never push to `main`: branch, PR, the user merges.
- Re-capture fixtures: `scripts/capture-fixtures.sh` (scrubs the username and IPs; journal fixtures are synthetic, never captured)
- Install: `make install-binary` (copies `target/release/sentry` to `~/.local/bin/sentry` and links `sentry-server` and `sentry-network` to it; `uninstall-binary` removes all three)
- Try a collector: `cargo run -q --bin sentry -- collect ostree`; a job plan: `cargo run -q --bin sentry -- job cleanup-flatpak --dry-run` (one binary; the server's commands: `cargo run -q --bin sentry -- server collect <name> probe`; the network's: `cargo run -q --bin sentry -- network collect probe`)
- Manual TUI tests: point `XDG_DATA_HOME`/`XDG_CONFIG_HOME` at a scratch dir so reports, the log, tasks.toml and baseline.toml stay out of the real ones

## Notes
- `XDG_CACHE_HOME` may be set (some dev shells set it): caches then live there, not `~/.cache/sentry`.
- Render tests: `crates/sentry-local/src/tui/screens/tests.rs` builds a `DataStore` from fixtures; snapshots in `crates/sentry-local/src/tui/screens/snapshots/`. The store's `tasks`/`maint_log`/`plans`/`snoozes` exist only in tests: `App::for_test` moves them into the slot's `Shared`, where the app keeps a target's records; screens read those through `View.sh`.
- `assets/workflows/*.toml` are embedded and seeded to `~/.config/sentry/workflows/` when missing; `release-rebase` is `draft = true` (no rebase has been run end to end).
- Workflow tests: put a harmless TOML in a scratch `XDG_CONFIG_HOME`, run with `SENTRY_NO_REBOOT=1`, fake a reboot by editing `boot_id` in `state.json`. A unit test that starts a run for real (the scratch data dir holds one at a time) takes `runs_turn()` first (`crates/sentry-local/src/tui/screens/tests.rs`; the server's `startable`; the window's `local_wf`), and ticks only its own rows: the updates row is the real quick-update.
- Screens: `1` Dashboard, `2` Processes, `3` Network, `4` Containers, `5` Flatpaks, `6` Maintenance, `7` Cleanup, `0` Upgrade, `H` History. Maintenance (`crates/sentry-local/src/tui/screens/maint.rs`) ranks `crates/sentry-local/src/maint/local.rs` (pure) recommendations (both engines end in `maint::rec::finish`: tasks due join, a task and a rule on the same `Target` become one row, snoozes drop, rank by level; both draw and hint through `tui::maintlist`, whose `Verbs` say which keys a row takes): findings, updates (Enter = `quick-update`, the one apply path; the TUI never offers `update-apply`), a staged reboot, tasks due (jobs' cadences are derived tasks: `jobs::state::tasks`; `tasks::effective` puts tasks.toml over them), failed jobs, cleanup, a run in progress, ready plans. Job runs, reboots, fixes and toolbox upgrades are `LogEntry::event`s in the log (`jobs.json`/`cadence.toml` are migrated once, `jobs::state::migrate`). The old Audit screen is a view inside it (`F`, `Maint::view`); Cleanup stayed a screen (the cleanup recommendation and `C` go there); `updates.rs` is only helpers (deployments panel, rollback, what's waiting). The cursor follows its row by key (`Maint::sync`); while that row is away (the updates' row is withheld during quick-update, and the run's own row comes in on top) it waits on the nearest row that was after it (`Maint.order`), else before, and goes back when the row does; a key on the list takes the row under the cursor (`take`). It used to adopt whatever sat at the old index: the first row, after a run.
- `crates/sentry-core/src/maint/` is shared by every target: the log + `LOG.md` ledger, plans, reviews (server `""` = this machine: `~/.config/sentry/{log,plans,reviews}/`; a server's under `servers/<name>/`), snoozes, `Level`, and `retention` (`[retention]` in config.toml, pruned at TUI start and after writes). Reviews are written by `docview::Writer`; local prompts in `crates/sentry-local/src/tui/plans.rs`. Plans are kept by apply sessions. Tasks (`crates/sentry-core/src/maint/tasks.rs`, `tasks.toml` beside the log): a review ends with a ` ```sentry-changes ` TOML block (`crates/sentry-core/src/maint/changes.rs`: add/remove/change a task, later/back, and on a server track/untrack/ignore/item; `take` validates against `Known` and drops with a reason) → `ReviewHead.changes`; the review window (`crates/sentry-core/src/tui/reviewview.rs`, `R`: brief → Enter starts → the changes ticked, Space unticks, Enter applies them together through `changes::settle`/`apply`, one `kind = "review"` log entry; no confirm box) is the same in every target (`review_open`/`review_start`/`review_apply`: `sentry-app`'s `slot/review.rs`); both rule engines turn due tasks into `task:<id>` rows (`Action::Task`); done is read from the log (the workflow/item change ended well, or `d` → `LogEntry::task`, tagged `task:<id>`). Enter on a by-hand task is an apply session (without Claude, its steps); `m` shows its steps and offers mark done. Tests use `App::for_test` (`win.offline`): nothing is written or sent.
- The frame (`crates/sentry-core/src/tui/frame.rs`, every target draws through it; `sentry-app`'s `Prompt` (`effect.rs`) is `WfVar`/`LogNote`/`LogAddNote`/`TaskEvery`/`TaskNote` and `Own` (a target's own: `Target::on_prompt`; sentry's workflow values), handled in `submit`/`cancelled` (`slot/core.rs`); `Ways.label` rewords one): `layout` (top bar, strip, rule, banner row, body, rule, key bar; under 80×24 a placeholder), `draw_top`/`draw_tabs`/`draw_banner`/`draw_keybar` (hints fitted, the toast at the right for `TOAST_FOR`), `help_modal`, `quit_modal`, `claude_choice`, `draw_run`/`run_key`, and `layer(&Open)`: the one order whatever is open gets keys and pastes and names the key bar's hints (Unlock → Run → Choice → Modal → Apply → Chat → Input → Docs → Screen; `Slot::open`; Unlock is the sudo password typed in the key bar). `tui/input.rs` is the one input line (`Input<P>`: filter, command, a `PromptLine`; Backspace on nothing closes a filter or command, never a prompt); `tui/modal.rs` has `Choice<E>`, `answer` (Enter/y, Esc/n/q) and `pick`. `ScreenId` (`tui/mod.rs`) is every screen any target has (`Svc` is the server's `5`, `Clients` the network's `2`, in no set yet); each declares a `ScreenSet` (`SCREENS` in its `tui/mod.rs`: strip order, aliases, `from_name` by slug, short name, alias or a 3-letter prefix) and `Keymap::new(&SCREENS, &cfg.keys)` binds only those (`[keys] screen.<slug>` of the other program's screen is skipped quietly). `Cursor` lives there too.
- One window, several targets (`crates/sentry/src/tui.rs`, `crates/sentry-app/src/app.rs`): `sentry` opens this machine plus a slot per server in `server_config.yaml` and per network in `network_config.yaml` (neither file: this machine alone, no strip, today's sentry); `sentry-server [name]` / `sentry-network [name]` the same window on that target (`tui::Open`, `plan_all`). `[targets] show = ["local", "srv:<name>", "net:<name>"]` (core `config::Targets::pick`) orders and hides them; a server or network asked for by name opens even when left out. The strip is in the top bar (`frame::Top.targets`, `TargetTab`, `Mark`; none with one target; names cut, then keys only, when narrow): key, name, `*` at work, `!` needs you, `auto`. Keys are the window's (`Keymap::target`, never `resolve`): `F1`… by place, `{` / `}` round (`[keys] target.<n>`, `target.next`, `target.prev`), taken before the slot except that a character is text where text is typed (`Slot::takes_text`: password, session, chat, input line); `:local`, `:server <name start>`, `:net <name start>` (`Ident.word`; `:net` alone is the Network screen of a target that has one, since a target's screen names come first; `Win.target_cmd`, after the target's own `:` commands and screen names). Each slot has its own keymap, screen set and input line: `Slot::park` swaps them with `Win.keys`/`Win.input`, so inside a flow `w.keys`/`w.input` are always that slot's (a prompt stays with the target that asked, text kept). A slot that never had the window is `asleep`: `App::start` only picks up its run left in progress (`Slot::pickup`); its records, first fetches and review at start come with its first focus (`Slot::shown` → `start`; later focuses → `enter(screen)`).
- Parallel across targets, one after another within one: every slot's events land in it whatever is in view (`App::with`), `App::tick` ticks every slot (run, session limits, timeouts), `next_due` asks every slot; only the slot in view polls for its screen (`Cx.focused`; out of view `Slot::enter` fetches nothing). A run goes on off screen `0` and out of view (no in-view rule; `Ways.auto_polled` is only whether the next auto step is also looked for on ticks). `Slot::needs(line)` → `Needs::{Nothing, Working, You(what)}` is the strip's mark; a slot out of view that comes to `You` is flagged and said once (`App::flag`: "<target> · needs you: <what>"), and never gets keys: its boxes, session window, prompts and password line are drawn and answered only in view (the password prompt names the target when there are several; `C-f` forgets the one in view). Toasts from a slot out of view carry its name (`Win.speaker`). Auto keeps answering out of view what `auto::answers` allows; the rest waits and flags. This machine's reboot ends the TUI (`Ways.reboot_ends_tui`): `wf_exec` holds it while another slot is `Working` (`Win.others_working`, `Slot.reboot_held`; the run's log and the banner say for whom) and `reboot_when_settled` sends it from `tick`. `q` with several targets lists what each has going (`App::quit_box`, `Slot::going`); shutdown is per slot as before. The terminal is handed over only for the slot in view (`App::handed`); the others' events queue. The locks (`runs_turn`, `startable`, one run per target's `runs` root) are per target. Tests: `crates/sentry/src/tests.rs` (`two_with(server, sudo_asks)`: this machine + a synthetic server per test, since runs are kept by name; `local_wf` serialises this machine's runs), `live_two_targets`.
- What can wait (every target): `Rec.can_wait` marks a rule nothing asks for yet (server: `Behind`, updates without a security fix, unknown/track/gone; sentry: Flatpak/toolbox-only updates, tidy cleanup); `rec::needed(recs, everything)` drops those and every `Level::Tidy` row (low findings, tidy tasks) from each screen's `recs(v)` (`View.everything`, `o` → `Effect::Everything`); reviews and Claude get them all (`recs_all` / `view_all`, `every_rec`). A due task absorbs a waiting rule of its `Target` in `finish`, so its row shows. A derived task (cadence, job) that never ran counts `every` from the log's first entry (`tasks::counted_from`); one from tasks.toml is due at once.
- A series (every target): `Maint.ticks` (`maintlist::Ticks`, row keys; Space / `a` / Esc, only rows whose `Verbs.series` is set) → Enter → `Effect::SeriesStart` → `maint::series::Series` in the slot beside `apply` (`slot/series.rs`). `series_go` resolves the row it's at from the live list by key (gone: skipped) and opens it: a session (`Session::start_in_series`: no Brief Enter, `Fx::Next` when it settles done or the user goes on; `Fx::Close` on it stops the series), a workflow (started; `series_run_ended` in `wf_log` / `wf_log_change` goes on or stops, and no `LogNote` is asked while a series runs), an audit; an item's row is just a session (on its ready plan when one is saved; one that answers "wait" is skipped). `series_end` / `series_stop` leave what isn't done ticked and run the one `review_after_run`. The banner row shows `Series::line()` when no workflow banner or visible session does. Tests: `ticked_rows_are_done_one_after_another` in each target's tests (and `…_on_each_target` in the window's).
- Records (`crates/sentry-core/src/tui/records.rs`, every target; `v`, `:log`/`:tasks`/`:plans`/`:reviews`/`:later`): one overlay, sections Tasks · Log · Plans · Reviews · Later; it returns `records::Fx`, mapped in `slot/records.rs` (`records_key`; a target's own rows through `Upkeep::records`/`undo`). Snoozes are `maint::later` (`later.toml` under `maint::root`; old `maint.toml` / `servers/<n>.maint.toml` migrated on load). Over Records, a plan or a review, screen keys and `:` still work.
- Apply with Claude (every target) is one session: `crates/sentry-core/src/apply/` (`plan.rs` the ```` ```sentry-apply ```` plan + `Run`; `session.rs` the state machine Brief → Investigating/Fix → Review → SudoCheck/Password → Applying → Verifying → Settled, returning `Fx` for the app to carry out; `verdict.rs` the ```` ```sentry-verdict ````; `sudo.rs` root edits under /etc, the password `Secret`, `wrap`/`wrap_ready`/`no_prompt`/`detached`) and its window `crates/sentry-core/src/tui/applyview.rs`. Its plan's steps and a workflow run's (screen `0`, both programs) are drawn by `crates/sentry-core/src/tui/stepview.rs`: the header (target · what · auto, then `State::words`: running / waiting on you · Enter … / done / failed), `row` (mark, number, title, kind, time taken), the running step's output under its row (`output`, `running`); `run_rows`/`run_state` for a run, `applyview::state` for a session. Opened by `A` → 1, the Plan view's `A` → 1 and Enter on a by-hand task (`Effect::AskConsent` with an apply `Ask`); the slot holds `apply: Option<Session>` beside `chat` and maps `Fx` in `apply_fx` (`slot/session.rs`; commands through `Host::command`: local `Cmd::host` bash; server: `remote.sh`, edits only local files, `Apply.remote`; local's re-audit after a finding's plan is `Why::Reaudit` → `Effect::Reaudited`). A session whose `Apply.plan` is set (an item; here, a workflow) researches first (`claude::apply_question`: the ledger, the notes, the web), and its plan is kept under that key in `plans/` (`Fx::PlanSave` → `Slot::plan_keep`, the assessment + the plan's block; `plans/done/` when done); a ready plan on disk opens the session on it (`Slot::session_for` → `Session::seeded`: Review at once, the brief sent with the first turn; a document from before, as its workflow with its values); `p` reads the saved plan, `P` starts over (`Effect::PlanAgain`). A `sentry-verdict` with `status = "wait"` settles with nothing changed (`End::Waited`, `Fx::Wait`: later.toml for `again` or 30 days, the plan document `wait`, a `kind = "wait"` log entry). No plan writer: `docview::Writer` writes reviews only. Only start and approve are keys; problems, failed steps and verification go to Claude by themselves; `done` tags the apply log entry `task:<id>`; a verdict's `[follow_up]` becomes a one-time task (`Fx::AddTask`) with `Task.after` (a workflow's next good run, or a wait like `7d`; `tasks::waited`). Tests: `offline` spawns nothing; `apply_answer_for_test`, `apply_step_exit_for_test`/`apply_exit_for_test` drive it.
- One session, every target (`crates/sentry-app/src/system.rs`, `slot/guest.rs`; core `apply/{plan,session}.rs`): a session is not confined to the target it started on. A ```` ```sentry-apply ```` step takes `on = "<target id>"` (`""`/`local`, `srv:<name>`, `net:<name>`; absent or the session's own id: the home target, kept as `None`; an id the window doesn't have is a problem sent back with the ids there are: `Session::place`), `capture = "<name>"` (run/check only: the last non-empty line the step prints on stdout, trimmed, kept for the session's life; one line, no single quote, no control character) with `secret = true`, and there is a fifth kind, `ask = "<name>"` + `prompt` (+ `secret`): the one way a value comes from the user (`Phase::Value`: typed into the session's own line, dots when secret, the plan goes on by itself; Esc settles `End::Waited` with the reason, nothing put off; auto never answers it, `Asked::Value`). Later steps on any target use `{{name}}` (`plan::fill`: filled when the step runs; a value that isn't a plain word only inside single quotes; in a workflow step's `vars` too, though a secret only on a target that `hides`, since elsewhere a run's values are written into its state). **A secret is in the command that runs and nowhere else**: `Session::clean` takes it out of every output line, note, report, prompt and log body (`‹name›`), the plan keeps the placeholder, a secret capture's stdout shows as `‹name: hidden›`, a value captured on a target that scrubs (`Peer.hides`, a router) is hidden whatever the step says, and `Peer.masks` (the network's `guard::secret_tags`: `redact::secret_option` on any `section.option=value` in the line) turns a secret a plan's own line sets in plain into its tag wherever the line is shown or kept (it runs as written; sent back as a tag it is refused). The window has one `Sweep` every slot's `kept_entry`/`plan_keep` goes through, and `Asks::given` hands the values to a target that sweeps what it writes itself (the network's `given`, `workflow::begin_hiding`). Routing: the session yields `Fx::On(id, Fx)` (a command, sudo's checks, a workflow, that target's log entry); `Slot::apply_fx_on` puts a `Parcel` in `Win.outbox`, which `App::with` delivers after the flow (`Slot::parcel`). The other slot runs the step as its own (`guest_run`: `root_cmd` with ITS password, `Host::command` with its policy, each line through its `hides`) and sends lines and the exit back; its strip mark is `Working`, its banner row says whose step runs. One approval covers the plan: `Session::approve` makes sure of sudo on each target in turn (`Fx::On(id, CheckSudo)` → `Host::sudo_asks`; `sudo_for`: the password is typed in the focused session's line, naming the target, checked and then held by that target's slot, never left waiting for focus). A slot busy with its own run, session or pane makes the step wait (`GuestWait`, "waiting for <target> to finish <what>"); after `GUEST_WAIT` (120 s) the session hears it never started (`Session::step_deferred`: no fix round spent). A workflow step `on` another target starts that target's workflow (`Parcel::Workflow`, `guest_run_ended`); its confirms are answered on that target. What Claude knows: `App::survey` (every 5 s with several targets) asks each target for `Asks::peer` (id, title, `refuses`, `asks_each`, `hides`, `calls`, `masks`), `Asks::describe` (`SystemLine`: kind, what, and `addrs`/`knows`, matched by the app and never printed: `system::links` says a server is the host a network's router calls ‹name›, in its DMZ, the destination of a forward) and `profile(ProfileFor::Peer)`; `system::merged` is the session's profile: its own target's, plus each other target's gateway and system text, with the union of every target's denials (so with a router in the window no session has the web, and its files stay closed), plus `system::HANDS` on every target, alone too (never tell the user to enter, paste, set or run anything; capture or ask). This machine, for a session that started elsewhere, allows nothing by itself (a read is a request; a change is a step `on = "local"`). Rules follow the step, not the session: `new_plan` asks the step's own target's `refuses` (a router's `Guarded`/`WorkflowOnly`/`Never` are refused in any session's plan exactly as in its own), every target's rule for a local file or command, and requests go by `Grant.on` (the gateway that refused, `claude::gateway_target`; None: this machine). ## Rules
- **No background processes**: no systemd units, timers or autostart. Threads die with the TUI. Two bounded exceptions, both remote and both ending by themselves: ssh's multiplex master (15 s, see sentry-server) and a router guard's dead-man (at most `guard.window`; its snapshot and one-shot boot hook sit on the router's flash for the same time; see sentry-network).
- Every external command goes through `exec::Cmd` (`Cmd::host` for host userspace; `Cmd::bytes_to` hands a command's stdout to a `Write` as raw bytes, for a binary stream). Never call `std::process::Command` directly. Dev happens in a toolbox, where `Cmd::host` adds the `flatpak-spawn --host` prefix.
- Host `/etc` is read via `paths::host_root()`.
- Collectors: a pure `parse()` (fixture-tested) and a `collect()` (exec + parse). A missing binary is `CollectError::Unavailable`, never a panic.
- Slow or network collectors run only on `c`/`r` and are cached (`cache.rs`). Nothing refreshes unless its screen is visible.
- Destructive actions: preview → confirm modal → streamed output.
- Never run `rpm-ostree upgrade/rollback/rebase`, `systemctl reboot`, or podman rm/stop for real while developing.

## sentry-server (`crates/sentry-server/src/`, `crates/sentry-server/src/main.rs`)
- A second kind of target (a library; `sentry-server …` is the one program under that name): monitors a server over ssh (`exec::Cmd::ssh`; its `remote::Remote` wraps `sentry_app::remote::Remote` with `cfg` and `inventory` and derefs to it; `workflow.rs` keeps `cond`, `RemoteEnv`, `BUILTINS`, `SEEDS`, `resume`/`begin`; `audit.rs` `derive`/`run`; `gateway.rs` `READ_ONLY`/`allowed`/`runnable`), configured by `~/.config/sentry/server_config.yaml` (sample: `assets/server_config.example.yaml`).
- **The repo is public: nothing about the developer's real server goes into git** (names, IPs, services, containers, ports, disks), nor into commit messages or release notes. Server fixtures in `tests/fixtures/server/` are synthetic (real formats, invented content: `myserver`, `app.service`, `stack`, 192.0.2.x). Captures from the real server go only in the gitignored `tests/fixtures/server/local/`.
- Run `make privacy-check` before every commit and release (patterns live in the gitignored `.private-patterns`).
- Against the real server, only read-only commands while developing; anything that changes it is exercised up to its confirm modal. Mutating mechanics are tested against a disposable local sshd container.
- sudo may ask for a password (the developer's server does): `Host::sudo_asks` (`fresh_sudo`) is looked up again before each thing that needs root; see "One sudo password per target". No terminal handover, nothing tee'd to the server.
- The inventory (`crates/sentry-server/src/inventory.rs`, key `I`): the collectors' own sudo argv run once in one `sudo sh -c` (`Effect::RootRead`, parsed from the command's own output), cached; read again by itself after a run when the password is held; `Remote::output` answers a refused `sudo -n` from it only when `Remote::inventory` is set (the TUI), never for workflow conditions.
- Maintenance (`crates/sentry-server/src/maint/`, screen `6`, `sentry-server maint`): `maintenance:` items in the config; the server's side in `local.rs`, upstream (curl from this machine: GitHub releases, Docker Hub, GHCR, endoflife.date) cached daily in `upstream.rs`, pure `eval.rs` → flags and `srv:maint:*` findings. - Claude's reads that need root: the gateway queues them in `$XDG_RUNTIME_DIR/sentry-server/reads-<server>.jsonl` (the runtime dir is the same for the TUI and Claude's child processes); after a turn the TUI runs them in one `sudo sh -c` (`root_reads`: at once when the password is held, else the one prompt, which names them) and sends the output as the next turn. Plans are a session's (see the apply-session paragraph): `apply_plan` → `ask::apply_item` (`Apply.plan` = the item), `Asks::plan_head` gives a new document its header (`maint::plan_doc`), `servers/<name>/plans/<item>.md` (`crates/sentry-core/src/maint/plan.rs`: `+++` TOML header, then Markdown); `planview.rs` is reviews only. The Plan view renders the document; applied, dropped or started over (`P`) plans move to `plans/done/`.
- Processes (`2`, `crates/sentry-server/src/tui/screens/processes.rs`, drawn by core `tui::proctable` like sentry's): `Kind::Procs` (`collect/procs.rs`: the probe script + `id -u` + `ps` + an awk over `/proc/[0-9]*/stat`, one exec without sudo every 2 s while the screen is shown, the second sample after 1 s). `ps`'s %CPU is a lifetime average, so `Rates::procs` computes `100 · cores · Δticks / Δtotal` against the probe's aggregate cpu line (first sample NaN → `–`; a new or reused pid 0; kernel threads left out by `PF_KTHREAD`); the same sample feeds `Store::on_probe`. Sections are cut at lines equal to `@@ps` / `@@ticks`. `x` (kill, as in sentry): a confirm box with `proctable::kill_lines` and the command; the login's own process is `kill -TERM`, another user's goes through sudo (`RunSpec.root`; `Screens::uses_root` looks at the selection so sudo is checked first). `collect::procs::kill_script` first compares `/proc/<pid>/stat`'s start time with the sampled one (`process <pid> is gone` otherwise). pid 1 is refused; an ancestor of the sampling shell (`@@self` = `$$`, parents from the awk's fifth field: `lineage`) is our own ssh session or the ssh server and gets the hard-to-undo warning. Never past the box on a real server; `live_actions` (disposable container) kills a `sleep` through it. Its per-sample cost on a real server is unmeasured.
- History (`H`, `crates/sentry-server/src/tui/screens/history.rs`, drawn by core `tui::histview` like sentry's; in the strip once `ServerTarget::has_ring`): the ring is on this machine, `<data>/servers/<name>/metrics/ring.bin`, sentry's format, fixed 10 s / 72 h (`crates/sentry-app/src/remote/recorder.rs`; the server's `recorder.rs` adds its disks/temperature/GPU sampler). - Maintenance review: `maint/discover.rs` (untracked / gone), `maint/tracked.rs` (`servers/<name>/items.toml`, merged in `Remote::new`), `maint/recommend.rs` (pure rules → ranked recommendations with actions; `maintenance.cadence` entries are derived tasks, `server::maint::cadence_tasks`), `crates/sentry-core/src/maint/review.rs` + `R` (Claude review, same writer as plans; its changes are applied in the review window: tasks to `servers/<name>/tasks.toml`, items through `tracked::apply`, where `untracked` and `[set.<id>]` in items.toml apply over the YAML's items, which are never rewritten). ## sentry-network (`crates/sentry-network/src/`)
- A third kind of target (a library; `sentry-network …` is the one program under that name, `crates/sentry/src/network.rs`): a home network through its router, OpenWrt over ssh as root. `remote::Router` wraps `sentry_app::remote::Remote` (`Privilege::Root`, scope `net:<name>`, `.dropbear()`) with its `cfg` and derefs to it. Built so far: the config, the collectors, the audit, Dashboard, Clients (`2`), Network (`3`), Maintenance (`6`: findings, tasks, the Items firmware / packages / backup), Upgrade (`0`: its workflows) and History, encrypted config backups, the recorder, the CLI, the policy and gateways, scrubbing, Claude (`tui/ask.rs`), the guard, and the workflows that change a router (`package-update`, `guarded-change`, `firmware-upgrade` as a draft). Not run end to end anywhere: `firmware-upgrade` (`owut`), and a guarded Wi-Fi change on a router with radios.
- **The repo is public: nothing about the developer's real network goes into git** (the router's ssh alias and hostname, SSIDs, addresses, MACs, device names, the ISP), nor into commit messages. Naming a router model as an example of a supported device is fine. Fixtures in `tests/fixtures/network/` are synthetic (real formats, invented content: `home`, `myrouter`, `Example Router AX`, 192.0.2.x / 198.51.100.x / 203.0.113.x, 2001:db8::, MACs 02:00:5e:00:53:xx). Captures from the real router, and the notes on what its busybox can and can't do, are only in the gitignored `tests/fixtures/network/local/` (`NOTES.md`: read it before writing a collector).
- Against the real router only reads while developing: what the collectors run, `sentry-network check|collect|audit|init|backup` with scratch `XDG_*` dirs (a backup made there is the real config, Wi-Fi passphrase and keys included: a throwaway key, and delete it and the backups afterwards), and the `#[ignore]` live tests. Never `uci set/commit`, a restart, `apk add/del/upgrade/fix`, `owut`, `sysupgrade` (but `-l` and `--create-backup -`), a reboot, a guard past its preflight (no arming, no `/tmp/sentry-guard-*`). Everything that changes a router is developed and proven against the disposable one (`scripts/live-router.sh`). `apk update` only as the user's `r` on Maintenance (and `live_refresh_index`, which needs `SENTRY_NETWORK_REFRESH=1`): it writes the tmpfs index cache, nothing on flash.
- Dropbear: `ssh -tt` with the local stdin at its end (what `Cmd::stream` does for a server) prints nothing and fails there. `Cmd::hold_stdin()` (set on every command a `Remote::dropbear()` builds) makes `stream` keep a stdin pipe open, unwritten, until the command exits (`Cmd::streamed`: the terminal, and whether stdin is held); stopping the local ssh still ends the remote command (`live_dropbear_stream` in `sentry-app`: gone within the first 250 ms check). Captured commands (`output`) and every other host are untouched. No `nohup`, `timeout`, `sudo`, `ss`, `jq`, `openssl`, `base64`, `curl` on the router, `ps` has no `-o`/`-e`, and busybox `sleep` takes whole seconds.
- Config (`config.rs`): `~/.config/sentry/network_config.yaml` (sample `assets/network_config.example.yaml`), `networks: <name>: { router: { ssh, kind: openwrt }, expect: { zones, forwards, listeners }, devices, thresholds, backup, maintenance: { items, cadence }, notes, claude }`. The whole shape is parsed and linted now (`lint`: names, forwards' proto/port/address, `proto:port@zone` listeners against the zones, MACs via `config::mac`, a `private_mac` device known by hostname, age/ssh recipients, ids and cadences), `guard: { window }` (5–3600 s, default 300) included. `backup.recipients` are checked by `backup::recipient` (a real age key, or a file of them; an ssh key is refused). `Ports` is one port or a range; `local_mac` is the locally-administered bit. sentry never writes the file; `init` writes it once.
- Collectors (`collect/`, each a pure `parse()` + a `collect()`, one ssh exec; `CollectError::Unavailable` for a command that isn't there, via `output_needing`'s `command -v … || exit 127`; `sections` cuts at lines starting `@@`): `probe.rs` = the shared `/proc` probe's files plus `/sys/class/net/*/{carrier,speed}` and the SoC's thermal zone, as one `awk` for the four multi-line files (`cat` each without awk) and the shell's `read` for the rest: no other fork. `Probe { host (the shared `remote::probe::Probe`, flattened), uptime (f64, the router's clock), ports: [Port { name, carrier, speed, rx_bytes, tx_bytes }], temp_c }`; counters are `/proc/net/dev`'s; `speed` is absent on lo and Wi-Fi and without a link (`-1`). `ifaces.rs` = `ubus call system board`, `system info`, `network.interface dump`, `network.device status`: `Board`, `Info` (load ×65536, `root_*` = the overlay in KiB), `Interface` (`gateway`/`gateway6` from the default routes, `lease_time_s` from `data.leasetime`), `Device` (`DevKind` from `devtype`, a Wi-Fi AP is `external` with none; speed from `"1000F"`), `wan()`/`wan6()`, `net_of(dev)` (its own interface, else its bridge's), `rows()` (the uplink's port, the wired ports, the radios; not lo, bridges, or the conduit the switch hangs off). `collect_json` backs `sentry-network collect`.
- More collectors, each one exec, 20–40 ms on the real router: `clients.rs` (`/tmp/dhcp.leases`; `/tmp/odhcpd.leases`, IPv6 by DUID, a MAC only in a DUID-LL; `ip neigh`; each bridge's `brctl showmacs` after an `@bridge <name>` line, its port numbers named through `/sys/class/net/<br>/brif/*/port_no` (hex there, decimal in brctl); per `ubus list 'hostapd.*'` its `get_clients` and `iw dev <if> station dump` for the connected time; → `Raw`; 10 s while Clients is in view). `listeners.rs` (`netstat -lntup` → core `net::Listener`, IPv6 bracketed as `ss` writes it, names cut at 14 as they come; entry and `r`). `uci.rs` (`uci show` one config per call for firewall dropbear uhttpd wireless dhcp network system, then `uci changes`; `parse(text, &Salt)` → `Uci { configs, staged }` with every secret already a tag; views `zones()`, `forwards()` (DNAT redirects, disabled too), `openings()` (ACCEPT rules without a dest), `dropbear()` (password logins on unless off), `uhttpd()`, `wifi()`, `staged_audited()` (only network firewall wireless dhcp dropbear uhttpd; not a dnsmasq option adblock-fast keeps staged beside its own lines); `show()` is the unredacted parser `init` uses for the firewall). `cert.rs` (`hexdump` of `uci get uhttpd.main.cert`, DER; `validity()` walks the ASN.1 to notBefore/notAfter, no crate). `services.rs` (`ubus call service list`; `state()`: `NotADaemon` for the instance-less ones in `NOT_DAEMONS`; `watched()` = dnsmasq, dropbear, uhttpd where installed + `expect.services`).
- CrowdSec's firewall bouncer (`collect/crowdsec.rs`, read only; nothing anywhere on a router without the package): its part rides the services' exec (`services::collect_with`: `@@crowdsec` printed only where `/usr/bin/cs-firewall-bouncer` or its init script is; `enabled` from `uci -q get crowdsec.@bouncer[0].enabled`, each family's elements counted on the router by an `awk` over `nft list table ip crowdsec` / `ip6 crowdsec6`, the process's age from `/proc`), so only counts come back. The fetch thread for `Kind::Services` sends `Kind::Crowdsec` too (never asked for by itself; `Store.crowdsec`, `Snapshot.crowdsec`). `net:crowdsec:bouncer`: switched on and no running instance (high); not switched on (low); running `CROWDSEC_EMPTY_S` with empty sets (low). Status row `crowdsec N blocked`. Names are from the OpenWrt package's source, the nft text is modelled (`tests/fixtures/network/crowdsec-nft-table.txt`); not yet seen on a real router.
- Redaction (`redact.rs`): `secret(option)` looks at the option's last name segment only (`key`, `password`, `psk`, `secret`, `token`, `private`, `pin`, `sae_password`, or ending `_<one of them>`; `PasswordAuth` and `key_type` stay readable). `Salt` = 16 random bytes in `networks/<name>/salt` (0600, made on first use); `tag(value)` = `redacted:<8 hex>` of SipHash-2-4 keyed with it (written out here, with the paper's test vector). - A secret a run is given is never written down (`guard.rs` `kept`/`secrets_in`/`swept`/`typed`, `redact::secret_option`): `workflow::begin` puts the tag in the run's vars (so `state.json`, the `$ …` line, the step logs, the log entry's Values and the card have it) and hands the real values to `Session::holding` (sentry-app `remote/workflow.rs`: `held`, in memory, rendered only into the command that runs). `Change::parse` refuses a tag where a secret's value should be (a resumed run, a kept plan: "start the change again and give the value") and never quotes a secret in an error; `Change::hider` sweeps what `preview`/`run` say and why they ended; `pending.json` has `Change::kept`. `NetworkTarget.given` (the secrets its runs were given) backs `Asks::kept` (log entries: `Slot::kept_entry`) and `plan_kept`; `Ways.typed` shows a value prompt's secret as dots. Tests: `a_guarded_changes_secret_is_never_written_down`, `secret_tests` in `workflow.rs`, the canary in `live_router_session`.
- Clients (`clients.rs`, pure): `merge((leases, leases6), stations, neigh, (fdb, &Topo), &devices, &seen) -> Vec<Client>` keyed by MAC; `Topo::of(&Ifaces)` says which devices are bridges, uplinks (their neighbours are the ISP's, never clients), radios, and each routed device's interface (`Link::Dmz { port, net }`). A device is there by a lease, a station entry, a bridge's table or an answering neighbour (a STALE one only adds addresses). `known` = `devices` names its MAC (an entry without `name:`, as `init` drafts, doesn't); a `private_mac` device's hostname labels a private MAC (never an identity). `unknown()` = not known and not (private on Wi-Fi); `flagged` = unknown, holding a lease, and `Seen` (`networks/<name>/seen.toml`: first, last, lease reads running up to 2) says two reads. `read()` = merge, `Seen::note`, merge. - Audit (`audit.rs`, `sentry-network audit [name]`): `Snapshot { ifaces, uci, listeners, clients, cert, services, errors }` (six execs; only ssh failing fails it), pure `derive(snapshot, cfg, prev, baseline)`, reports through `sentry_app::remote::audit` under scope `net:<name>`. `Exposure` (zones, openings, interfaces): `side(listener)` = Local / Any / Zone / Unknown (an address of an interface, the router's own address in an assigned prefix (`Interface.local6`), or a link-local one by EUI-64 when only one zone's devices share that MAC); `wan_open(proto, port)`; `expected_keys` turns `expect.listeners` (`proto:port@zone`) into baseline keys so the shared `listener_status` decides (a socket on every address that the outside can reach needs the uplink's zone named; a UDP port ≥ 32768 is a client's). Findings: `net:wan:down` high; `net:zone:<z>` medium, high when the uplink's zone accepts input or forward; `net:forward:<proto>:<port>` high, `net:forward:missing:<name>` medium; `net:listener:<proto>:<port>` high where the outside reaches it, else low (Tidy: listed with `o`); `net:ssh:password` medium (high when reachable from outside); `net:luci:http` medium; `net:cert:expiry` low within `cert_days`, medium past; `net:config:staged` medium; `net:client:<mac>` medium; `net:service:<name>` high; `net:mem-high` / `net:load-high` (5-min load) medium. `net:config:unsaved` (from `Snapshot.backup`, a `backup::Status` the audit reads with one more exec, `sysupgrade -l | xargs sha256sum`): the config differs from the newest backup (medium; evidence = the changed options, capped at 8, else the files), or there is none (medium; low while no recipient is set).
- Lease left (`Interface::lease_left`): netifd gives the lease's length and the interface's uptime, and a renewal doesn't restart that uptime. So `Exact(lease − uptime)` only until half the lease has passed; after that `Between(lease/2, lease)` ("renewed, 1h–2h left"). The plan's "lease − uptime" would be negative on any router up for a day.
- Rates (`rates.rs`, pure): `Rates::feed(&Probe)` → per port `Rate { rx, tx }` in bit/s = `Δbytes · 8 / Δuptime`, both the router's. The gateway's read rules are untouched: these sources are sentry's own reads. Polls: only in view and focused; the 10 s reads keep ssh's master (15 s) alive, so a minute of Security adds no login to the router's log (a screen whose only poll is 30 s, as Network's `Ifaces`, reconnects each time: three log lines a poll). `live_security` (`SENTRY_NETWORK_LIVE`, reads only; `SENTRY_LIVE_SCREEN=<file>` writes the screen, which names devices): the uplink's reject rate against two `nft list chain` readings by hand, every conntrack line a classified flow, every inside source in a zone. Measured on the real router: counters 42 ms, flows 21 ms, the log 75 ms, the status 223 ms; a minute of Security in view (release build, under a pty) costs this machine 0.17% of one core incl. its ssh children (the master 0.02%), 15 MB RSS; the router was 0.2 and 1.4 points of one core busier than the minute before in two runs (its idle minute itself moves between 1.5 and 1.8%); no dropbear line was added during the minute (entering the screen makes several connections at once: about five logins, once).
- `Upkeep` (in `tui/target.rs`): `derived_tasks` = `maint::cadence_tasks` (`maintenance.cadence` for the workflows there are), `with_known` the tasks and rows, `records` when it was audited, `undo` takes an expected finding back, `series_step` a workflow's run, the audit, or a session for a finding or a by-hand task (`maint::series_kind`), `item_kind` firmware/packages/backup, `changes` → `NoChanges`. `Host::command` is `router.sh(line)` unless `policy::refuses(line)`: then a local command that only prints why and exits 126, so whatever a plan or an allowed request says, a guarded, workflow-only or never line is not sent. `Host::reboot` is empty (no workflow has a reboot-kind step; a root login's reboot word is the target's, `remote::workflow::Words.reboot`: `reboot` here, `systemctl reboot` on a server).
- **Policy** (`policy.rs`, pure; `classify(line) -> Class`, `verdict` with why and, for a read, `run`; `verdict_argv` for `exec`'s words; `refuses`): root has no sudo line, so every line Claude sends is read before any connection. `Read < Change < Guarded < WorkflowOnly < Never`. **`Read` is decided positively and rebuilt** (`read.rs`, `read::plan`): a line is a read only when it parses under the grammar there, and then the router's shell never sees the line as written, only what sentry made from the parse. The grammar: simple commands joined by `|`, `;`, `&&`, `||`; a program on `read::PROGRAMS` (by name: never a path, `busybox x`, `env x`, a quoted-apart name is still the list's) with literal arguments its `rule` allows flag by flag (`getopt`: clusters taken apart, flags before operands, no operand starting with `-`); only `2>&1`, `2>/dev/null`, `>/dev/null`; single quotes and plain double quotes group. Outside it: `$`, backticks, backslashes, `#`, `~`, braces, parentheses, `<`, `&`, an assignment, a line break or control character, `$`/backtick/backslash in double quotes. A `*`/`?` outside quotes is a pattern only in a path under `read::GLOB_DIRS` (/sys/class/net, thermal, hwmon, ieee80211, /sys/devices/system/cpu, /proc/net, /proc/sys/net; no component starting with `.`, since ash's `.?` matches `..`), sent bare; anywhere else it puts the line outside (quote it to mean the characters); an unquoted `[0]` is literal for uci and grep. Paths are made plain first (`read::normal`: `//`, `/./`, `..` by its text; climbing above `/` or a relative path is outside) and the plain path is what is checked and sent. Files are printed only from `READ_FILES`/`READ_DIRS` (named /proc files, /proc/net, /proc/sys, /proc/<pid>/{stat,status,statm,comm}, a few /sys/class dirs, the lease files, a few of /etc): not /proc or /sys as a whole, never /rom/etc, /overlay/upper/etc, /proc/<pid>/root, /proc/self, /dev. **Only the first command of a pipeline runs on the router** (`Source::Remote`, one `prog 'arg' …` line each, every argument single-quoted here): the filters (`read::FILTERS`: grep/egrep/fgrep without `-o`/`-r`/`-f`, head/tail by lines, sort without `-o`, uniq, wc, cut) and a filter's own file (`grep x /tmp/dhcp.leases` = `cat` there, grep here) are done on this machine **after the scrubbing** (`filter.rs`, the `regex` crate; `grep` basic/extended/fixed translated): a pattern matched on the router is an oracle for what the scrubbing hides (`grep -c "key='a"`). For the same reason no program selects by pattern or address there: `logread -e` is a grep here, `ip … show` takes `dev <name>`/`default`/`table`/`up`, no `ip route get`, `pgrep` by name without `-f`, no `iw … scan [dump]` or `station get`. `echo`, `true`, `false`, `sleep` (≤ 30) are done here. Not on the list (so a request, never a read): awk, sed, tr, od, hexdump, strings, xargs, sh, env, `sysupgrade -l` (sentry's own, one at a time: `Never` through the gateway), `route`, `ifconfig`, `arp`, `top` but `-b -n 1`. Invariant test (`read/tests.rs` `whatever_is_a_read_sends_only_what_was_understood`): 150 000 generated lines of shell metacharacters with allowed and dangerous commands; whenever the class is `Read`, every line sent parses under an independent reference tokenizer into exactly the one simple command the classifier saw. **Everything else** is read by the older conservative lexer (`verdict_at`, now only choosing among the classes that don't run by themselves): a line is its worst part (`;`, `&&`, `|`, newlines, `$(…)`, backticks, `sh -c`, `eval`, `xargs`, every `find -exec`, a heredoc's body, redirections), an unknown program's arguments are read as commands of their own (`wrapped`), and a line the grammar can't take apart is also read word by word with every shell character a break (`by_words`: a `reboot`, `uci commit` or secret path in a quote, a comment or `$'…'` still decides). Paths are squashed first (`//`, `/./`). What is left is `Change`, shown as it will run. `Guarded`: `uci commit`, staging verbs on `GUARDED` configs, init verbs on `GUARDED_SERVICES`, `wifi`, `ifup`/`ifdown`, `fw4 reload`, nft with any flag but `-a -n -s -j -t -y` or a changing verb, ip/iw/brctl/route changes, `ifconfig` beyond one interface, `arp` beyond `-n`/`-a`. `WorkflowOnly`: `sysupgrade` (flash), `owut upgrade|install|download`, `apk upgrade`, `apk fix`, `apk add` of a base package or with `-u`, `reboot`/`poweroff`/`halt`. `Never`: `secret_path` (shadow, dropbear's keys, `/etc/config/*` raw, hostapd's files, flash and memory devices, `/proc/<pid>/{environ,root,cwd,fd,mem}`, `/sys/kernel/debug`, `/tmp/.uci`, anything named `sentry-guard`, `..`), `sysupgrade -b|-l`, `passwd`, `dropbearkey`, `firstboot`, `mtd`, `dd` to a device, `rm`/`find -delete` from the top, fetch-and-run, a write under /etc, /usr, /lib, /bin, /sbin, /overlay, /rom, /dev, /proc, /sys (`sort -uo/etc/x` too: the target follows the `o` in its cluster), `sysctl -w`, `kill` by number / `pkill -f` / a signal to a daemon the network is reached through or part of its name (`DOORS`), `apk del` of a base package or with `-r`, starting a listener (`telnetd`, `dropbear`, `uhttpd`, `nc -l|-e`, socat…), `tc`/`rmmod`/`insmod`/`ethtool -s`/`hostapd_cli`/`wpa_cli` and the like, any `uci` write to `rpcd`/`ucitrack`/`luci`, and a `uci` line that sets **an option that is a script run as root or a file a daemon reads, writes or serves** (`policy::runs_or_reads`, also refused in a guard line: firewall includes and `path`/`type`, dnsmasq `dhcpscript`/`*file`/`confdir`/`tftp_root`/`enable_tftp`, odhcpd `leasetrigger`, uhttpd `interpreter`/`*_prefix`/`home`/`cert`/`key`, dropbear `BannerFile`/`*keyfile`, `pppd_options`, `hostapd_options`, anything with `script`/`hook`/`command`/`handler`/`plugin`, ending in `file` or `_options`; the names are OpenWrt's from memory, not read from its docs).
- **Gateway** (`gateway.rs`; `sentry-network run <name> -- '<line>'` a session's, `exec <name> -- <argv>` a chat's and a review's: the words are one simple command, never parsed, never syntax): `runnable`/`readable` give a `read::Plan` or what the line is held for. `go`: the scrubbing is read first (`Scrub::read`, three reads; if it can't be made nothing runs), then `carry_out` runs the plan: each `Source::Remote` line alone over ssh (`r.sh(rebuilt)`), its stdout and stderr scrubbed at once, the filters applied here, `;`/`&&`/`||` decided here by exit status. `Change` → "requires approval: <line>" (126; a request, the line as written, which is what `Host::command` then runs) for `run`, refused for `exec`; the other classes → 126 with `Verdict::refusal`. A refused line makes no connection. `Host::command` sends a session's read through the same gateway (this program, `run <name> -- <line>`), a change as written, and what is never run nowhere. `SENTRY_GATEWAY_TRACE=<file>` (tests) appends every line sent, as sent.
- **Scrubbing** (`redact::Scrub`, `Facts`): everything of the router's that Claude sees (gateway output before any filter, `ask.rs`'s prompts through `hidden`, what a step, an allowed request or a workflow's closing note said through `Asks::hides`, the guard's shown lines). Per line: a secret option's value → its tag in `uci show`, `uci export`, `name=value` and JSON however laid out (`secret()`: last name segment `key`, `key1`–`key4`, `password`, `passwd`, `passphrase`, `pwd`, `psk`, `pmk`, `secret`, `token`, `private`, `pin`, `pincode`, `apikey`, `sae_password`, `r0kh`, `r1kh`, or ending `_<one>`); any value whose tag is one the config was read with (`known`: words, quoted strings, runs of up to six words); the word after `password` in a command line (`pppd … password x` as `ps` shows it); a private key block and a password hash dropped. **Addresses and MACs are parsed and compared by value, not text** (`nets`/`net_at`): the uplink's addresses → `‹wan›`/`‹wan6›` in any spelling (upper case, expanded, zoned, `::ffff:` in front, a port behind), its gateway → `‹wan-gw›`, anything else on the uplink's network → `‹wan-net›` (IPv6: the on-link prefix and delegated prefixes are `‹wan6›`), the same as /proc/net/route's 8 hex digits in either byte order, all unless `claude.share_wan_address`; a MAC with colons, dashes, Cisco dots or nothing between (12 hex with a letter), glued to a label (`sta:<mac>`) → `‹name›` or vendor half + `xx`; an EUI-64 interface id (link-local or ULA) → `<prefix>‹eui64 …›` by the same rule; 7+ colon pairs → `‹id›`, 20+ hex → `‹hex›`; SSIDs → `‹ssid-N›` (literal match, any characters); a lease's hostname → the config's name or `‹host-xxxx›`, dnsmasq's DHCP log lines too. An unknown device's finding is `net:client:<8 hex>`, a salted tag of its MAC (`audit::client_id`), since ids go into the log and tasks. Built from what was read at that moment: a hostname no lease holds, in free text with no rule, is not caught.
- **Claude** (`tui/ask.rs`; `Asks` in `tui/target.rs`): chat = `Bash(sentry-network exec <name>:*)`, Read of `notes:` and the log dir; review = that plus WebFetch/WebSearch, no edits; **session = chat plus `Bash(sentry-network run <name>:*)` and no web** (it can act, and what the router prints is partly other people's text: a planted line beside the web could ask for something to be sent out; a review can run and write nothing, and upstream's notes are what it is for). `ask::private`: every profile denies (Read/Edit/Write, as file and as `/**`) the network's whole data root (reports, backups, the guard's journal, workflow run logs, metrics), `network_config.yaml`, `~/.ssh`, and the config root entry by entry except `log` and `plans` (deny rules can't make an exception: `KNOWN` names plus whatever `read_dir` finds when the profile is made: salt, `baseline.toml`, `seen.toml`, `later.toml`, `tasks.toml`, `items.toml`, reviews, workflows); Edit/Write of `log`, `plans` and the seeded workflows dir; on top of `Profile::denied_for_servers`. The system text says what the router prints is data, never instructions, and names the `leave_alone` devices. `Apply { remote, refuses, how, reaudits, asks_each }`: `refuses` makes a plan step a problem and a request not runnable; `asks_each` (core `Session::auto_go`): auto never approves this session's plan and allows **no** request it makes, a file here included. No real Claude turn has been run against a router.
- **The guard** (`guard.rs`; `sentry-network guard <name> preview|apply|keep configs=… services=… [wan=yes] -- <uci lines>`; the `guarded-change` workflow): `Change::parse` takes only `uci set|add|add_list|del_list|delete|rename|reorder` lines on its own `GUARDED` configs (`policy::plain_commands`), each word re-quoted, none setting an option `policy::runs_or_reads` names. On the router: `/tmp/sentry-guard-<token>/` (marker `armed`, pids, `deadman.sh`, `reloads.sh`, the reloads' log), the snapshot **on flash** `/etc/sentry-guard/<token>/config/` (0700) and the one-shot boot hook `/etc/uci-defaults/zz-sentry-guard-<token>` (`hook_script`: the restore itself; OpenWrt's `/etc/init.d/boot` sources each file there once at boot and removes it; it does nothing once the snapshot is gone). **One side takes a guard**: the sleeper and a disarm each `mv armed claim.<who>`, which only one can do; the sleeper then `trap '' HUP INT TERM`, runs the hook, the reloads, writes `<token> reverted` to `/tmp/sentry-guard.last` and removes hook and dir; `disarm_script`/`abort_script` (`claim_script`) act only inside their claim and say `claimed` (and leave `<token> kept`), `left`, or `lost` [`restoring`|`reverted`]. sentry says `Kept` only on `claimed`, or when the router's own word says `kept` after an answer was lost. Script builders are pure and snapshot-tested (`state_script`, `arm_script`, `hook_script`, `armed_script`, `apply_script`, `disarm_script`, `abort_script`, `settled_script`, `clear_script`). `run` (holding `guard::turn`, a lock in `<data>/networks/<name>/guard/`: one at a time from this machine): `clear_script` (what an earlier guard left with no live sleeper, judged by `/proc/<pid>/cmdline`, is restored if it has a snapshot and cleared; a live one is left and stops the run) → preflight → arm (snapshot, hook, marker, `sync`, sleeper) → verify on a new connection (marker, both pids, snapshot, hook) → apply → poll on new connections until `window − margin`: `confirm` (answers, reloads exited 0, **no interface newly `pending`**, uplink and routes as before unless `alters_wan`, closed zones still closed, expected forwards there) must hold **twice, `settle_gap` (1–3 s) apart, with the same interfaces, addresses, routes and firewall** (a reload returns before netifd has finished) → `disarm` (given `margin − 1` s to answer; never started within `margin` of the deadline) = `Kept`; wireless or `alters_wan` → `Waiting` (`guard/pending.json`), `keep` disarms; anything else → `settle` (does nothing, then reads the router's word) → `Kept`/`Reverted`/`Failed`/`Unknown`. `auto::never` names `guard apply`, `guard keep`, `firmware flash` and `packages upgrade base` under either program name. Not checked by `confirm`: that the nft ruleset loads, new forwards or rules the change adds, Wi-Fi itself. Not shown live: an early confirm (the container's interfaces have no devices, so nothing is ever pending there).
- **The dead-man is the second bounded exception to "no background processes"**: one `sh` and its `sleep` on the router, started by `arm_script`, gone at disarm or after `guard.window` seconds. **And the guard's snapshot is the one thing sentry writes to a router's flash besides the change itself**, bounded the same way: per guarded change a copy of each config it touches and one hook script (measured on the disposable router: 8 KiB for two configs, a 741-byte hook), deleted when the change is kept or taken back; a restart in between runs the hook, which restores, deletes both and leaves one line in `/etc/sentry-guard.last`. Nothing else of sentry's stays on a router.

- Measured (release build, under a pty, the network Dashboard in view for a minute): 0.67% of one core incl. its ssh children and the multiplex master (0.57% without the master), 12.2 MB RSS. On the router (4 cores; `/proc/stat` over a minute with and without the probe running): busy 4.0–4.3% of one core by itself, 5.3–6.2% with the 1 Hz probe, so the probe costs about 1.6% of one core (1.2 and 1.9 in two runs; it was 2.3% with a `cat` per file, which is why the script is one `awk`). The script itself is 4 ms of the roughly 16 ms a sample costs there; the rest is dropbear starting a session and a shell.
