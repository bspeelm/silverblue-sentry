# sentry: Silverblue monitor & maintenance TUI (Rust + ratatui)

Spec: `docs/spec.md`. Binding amendments: `docs/spec-addendum.md` (read both before changing behavior).
Design for M3–M7: `docs/design/m3-m7.md`.
Visual target: `docs/design/sentry-tui.dc.html` (read the source; don't render it).
Upgrade procedures: the user's personal notes in `docs/cheatsheets/` (gitignored, never commit or publish them) are the source for `assets/workflows/*.toml`.

## Layout
- Cargo workspace, one repo: `crates/sentry-core` (shared: exec, paths, config, baseline, finding, claude, maint records, workflow format + runner, disk/gpu/journal/net/procfs parsers, the TUI kit incl. the frame, chat, docview, maintlist, records), `crates/sentry-app` (what targets share beyond the kit: the app itself, below, and `remote/`: a host over ssh), the targets `crates/sentry-local` (this machine), `crates/sentry-server` and `crates/sentry-network` (libraries, each with a `testing` feature for the window's tests), and `crates/sentry`, the one binary (`main.rs` this machine's commands, `server.rs` the server's, `network.rs` the network's, `tui.rs` the window, `tests.rs` the targets side by side). Core never depends on the others; `sentry-app` depends only on core; targets never depend on each other; only `crates/sentry` depends on all three.
- One program, three names: called as `sentry-server` or `sentry-network` (argv[0]: the symlinks `make install-binary` makes beside it) or as `sentry server …` / `sentry network …` it is that command line (`main.rs` `as_command`), same output. A workflow step that runs `sentry-server cond …` finds it beside the program (`remote::workflow::exe`: `sentry server`); Claude's profiles call `sentry-server run|exec` from PATH (the symlink).
- `sentry-local` re-exports core under the old names (`crate::exec`, `crate::maint::log`, …); its `maint`, `workflows`, `collectors`, `tui` modules glob-re-export core's and add their own. sentry-server uses `sentry_core::…` explicitly (its own `config`/`maint`/`tui`/`audit` would clash).
- `crates/sentry-app/src/remote/` (moved out of sentry-server, which re-exports them under its old paths): `mod.rs` `Remote { name, host, scope, privilege, hold_stdin }` (`Privilege::Sudo { allow }`: `sudo -n` through the allowlist; `Privilege::Root`: bare argv, `sudo_mode()` is `SudoMode::Root` without an exec; `Remote::dropbear()` sets `hold_stdin`, see sentry-network), `Error` (the server's `SrvError`), `host`; `workflow.rs` (`Session` with a `Box<dyn Env>` and the program's name, `Session::on(Words)` for what it calls its host (default "the server"), `Exec`, `Live`, `tee_to`, `no_prompt`, `root`/`own_dir`/`pick_dir`); `probe.rs`; `recorder.rs` (`record(r, extras)`); `audit.rs` (`Report<S>`, the report store, `set_expected*`, `pattern_for(ns, …)`, `listener_status`/`listener_id`); `gateway.rs` (`SECRET`, `Held`, `words`/`commands`, `run_cli(prog, r, line, policy)`, the read queue); `upstream.rs` (GitHub, endoflife.date, `comparable`).
- `crates/sentry-app/src/` is the app (`sentry_app::App`, a slot per target): `target.rs` (`Target` with `Upkeep`/`Asks`/`Host`, object-safe: a target owns its fetch threads, kinds, store and screens; `Ident` its names and words; `Ways` where a program's flows go their own way: words and rules such as `auto_polled` and `reboot_ends_tui`, default = the server's, each flow asks `self.ways`; `Cx` what it may look at, incl. `at`, the one clock (`Win.at`, the event's instant), and `focused` (the target has the window: only then may `due`/`next_due` poll for its screen); `Mail` how its threads and streams answer, tagged with its id; hooks with a default for what only one program does: `on_prompt`, `pane_ended`, `plan_key`, `plan_written`, `chat_continue`, `wf_start`, `session_starts`, `run_cmd`, `run_plan`/`run_info`, `find_workflow`), `app.rs` (`App { slots, focus, win }`, `App::new` + `App::add`; `Win`: theme, keymap, toast, the input line, the help/quit box; `Event` carries a target id; `App::with(i, …)` runs a slot's flow with the window as that slot sees it), `slot.rs` + `slot/` (`Slot`: one target, its `Shared` records, the screen in view, run, session, series, chat, writer, Records, its boxes; every flow is an `impl Slot` method taking `&mut Win`: `core` events/keys/`open()`/prompts, `effects`, `session`, `wf`, `series`, `review`, `records`, `draw`), `shared.rs`, `effect.rs` (`Effect`, `Prompt`, `WfCmd`; a target's own effects travel as `Effect::Own` and come back in `Target::on_own`/`after_suspend`), `run.rs` (`WfRun`: a workflow run as the app sees it; `remote::workflow::Session` is one, sentry's `tui/wf.rs` `Session` the other; `Exec::Stream { dry, timeout }`, `Shell`, `Live.deadline`). Its `testing` feature holds the tests' helpers (`apply_answer_for_test`, `writer_answered`, `render_to_string`…). The server's side: `crates/sentry-server/src/tui/target.rs` (`ServerTarget`, its `Own` effects, `testing::{srv, wf, data_ev}`) + `target/upkeep.rs`; `tui::target(remote)` is what `App::new`/`App::add` build it with (`tui::app(remote, tx)`: the server alone, the tests'). This machine's side: `crates/sentry-local/src/tui/target.rs` (`LocalTarget`: the store, the schedule, `lift` turns the screens' `tui/app.rs` `Effect`s into the app's or sends them back as `Effect::Own` → `on_local`; reboot, `run_go`, rollback, baseline edits) + `target/upkeep.rs` (lists, Claude's profiles and requests, the workflow plans' box and keys); `tui::target(cfg)` likewise (`tui::app(tx)`: alone); `tui/app.rs` is only the screens' effect types and the tests' `App` wrapper (`for_test`, `*_for_test`).
- A scope (`maint::root`, `maint::data_root`, the ring, baseline): `""` this machine, a plain name `servers/<name>`, `net:<name>` `networks/<name>`; `maint::label` drops the prefix. Never build those paths by hand.
- Test support in core is behind its `testing` feature, enabled only through the other crates' dev-dependencies (scratch XDG dirs, `claude::TEST_AVAILABLE`). Fixtures stay in the root `tests/fixtures/` (`../../tests/fixtures` from a crate).

## Commands
- Build/test: `make check` (= `cargo build --release && cargo test && cargo clippy --all-targets -- -D warnings && cargo fmt --check`)
- Snapshot tests: `cargo insta review` (or `INSTA_UPDATE=always cargo test` and then inspect `git diff`)
- Tests run with `TZ=UTC` (`.cargo/config.toml`), so snapshots match CI; `cargo run` shows UTC times too unless `TZ` is set.
- Unit tests never touch the real config/data/cache: `paths::xdg` gives each test process a scratch root under the temp dir (XDG_* ignored). Live tests (`#[ignore]`) call `crate::paths::use_real_dirs()` first, which honours XDG_* again; a new live test must too.
- CI (`.github/workflows/ci.yml`) runs `make check` plus MSRV (1.95, set by sysinfo) and a privacy scan on every PR. Never push to `main`: branch, PR, the user merges.
- Re-capture fixtures: `scripts/capture-fixtures.sh` (scrubs the username and IPs; journal fixtures are synthetic, never captured)
- Install: `make install-binary` (copies `target/release/sentry` to `~/.local/bin/sentry` and links `sentry-server` and `sentry-network` to it; `uninstall-binary` removes all three)
- Try a collector: `cargo run -q --bin sentry -- collect ostree`; a job plan: `cargo run -q --bin sentry -- job cleanup-flatpak --dry-run` (one binary; the server's commands: `cargo run -q --bin sentry -- server collect <name> probe`; the network's: `cargo run -q --bin sentry -- network collect probe`)
- Manual TUI tests: point `XDG_DATA_HOME`/`XDG_CONFIG_HOME` at a scratch dir so reports, the log, tasks.toml and baseline.toml stay out of the real ones

## Notes
- `XDG_CACHE_HOME` may be set (some dev shells set it): caches then live there, not `~/.cache/sentry`.
- Render tests: `crates/sentry-local/src/tui/screens/tests.rs` builds a `DataStore` from fixtures; snapshots in `crates/sentry-local/src/tui/screens/snapshots/`. The store's `tasks`/`maint_log`/`plans`/`snoozes` exist only in tests: `App::for_test` moves them into the slot's `Shared`, where the app keeps a target's records; screens read those through `View.sh`.
- `assets/workflows/*.toml` are embedded and seeded to `~/.config/sentry/workflows/` when missing; `release-rebase` is `draft = true` (no rebase has been run end to end).
- Workflow tests: put a harmless TOML in a scratch `XDG_CONFIG_HOME`, run with `SENTRY_NO_REBOOT=1`, fake a reboot by editing `boot_id` in `state.json`. A unit test that starts a run for real (the scratch data dir holds one at a time) takes `runs_turn()` first (`crates/sentry-local/src/tui/screens/tests.rs`; the server's `startable`; the window's `local_wf`), and ticks only its own rows: the updates row is the real quick-update.
- Screens: `1` Dashboard, `2` Processes, `3` Network, `4` Containers, `5` Flatpaks, `6` Maintenance, `7` Cleanup, `0` Upgrade, `H` History. Maintenance (`crates/sentry-local/src/tui/screens/maint.rs`) ranks `crates/sentry-local/src/maint/local.rs` (pure) recommendations (both engines end in `maint::rec::finish`: tasks due join, a task and a rule on the same `Target` become one row, snoozes drop, rank by level; both draw and hint through `tui::maintlist`, whose `Verbs` say which keys a row takes): findings, updates (Enter = `quick-update`, the one apply path; the TUI never offers `update-apply`), a staged reboot, tasks due (jobs' cadences are derived tasks: `jobs::state::tasks`; `tasks::effective` puts tasks.toml over them), failed jobs, cleanup, a run in progress, ready plans. Job runs, reboots, fixes and toolbox upgrades are `LogEntry::event`s in the log (`jobs.json`/`cadence.toml` are migrated once, `jobs::state::migrate`). The old Audit screen is a view inside it (`F`, `Maint::view`); Cleanup stayed a screen (the cleanup recommendation and `C` go there); `updates.rs` is only helpers (deployments panel, rollback, what's waiting).
- `crates/sentry-core/src/maint/` is shared by every target: the log + `LOG.md` ledger, plans, reviews (server `""` = this machine: `~/.config/sentry/{log,plans,reviews}/`; a server's under `servers/<name>/`), snoozes, `Level`, and `retention` (`[retention]` in config.toml, pruned at TUI start and after writes). Reviews are written by `docview::Writer`; local prompts in `crates/sentry-local/src/tui/plans.rs`. Plans are kept by apply sessions. Tasks (`crates/sentry-core/src/maint/tasks.rs`, `tasks.toml` beside the log): a review ends with a ` ```sentry-changes ` TOML block (`crates/sentry-core/src/maint/changes.rs`: add/remove/change a task, later/back, and on a server track/untrack/ignore/item; `take` validates against `Known` and drops with a reason) → `ReviewHead.changes`; the review window (`crates/sentry-core/src/tui/reviewview.rs`, `R`: brief → Enter starts → the changes ticked, Space unticks, Enter applies them together through `changes::settle`/`apply`, one `kind = "review"` log entry; no confirm box) is the same in every target (`review_open`/`review_start`/`review_apply`: `sentry-app`'s `slot/review.rs`); both rule engines turn due tasks into `task:<id>` rows (`Action::Task`); done is read from the log (the workflow/item change ended well, or `d` → `LogEntry::task`, tagged `task:<id>`). Enter on a by-hand task is an apply session (without Claude, its steps); `m` shows its steps and offers mark done. Tests use `App::for_test` (`win.offline`): nothing is written or sent.
- The frame (`crates/sentry-core/src/tui/frame.rs`, every target draws through it; `sentry-app`'s `Prompt` (`effect.rs`) is `WfVar`/`LogNote`/`LogAddNote`/`TaskEvery`/`TaskNote` and `Own` (a target's own: `Target::on_prompt`; sentry's workflow values), handled in `submit`/`cancelled` (`slot/core.rs`); `Ways.label` rewords one): `layout` (top bar, strip, rule, banner row, body, rule, key bar; under 80×24 a placeholder), `draw_top`/`draw_tabs`/`draw_banner`/`draw_keybar` (hints fitted, the toast at the right for `TOAST_FOR`), `help_modal`, `quit_modal`, `claude_choice`, `draw_run`/`run_key`, and `layer(&Open)`: the one order whatever is open gets keys and pastes and names the key bar's hints (Unlock → Run → Choice → Modal → Apply → Chat → Input → Docs → Screen; `Slot::open`; Unlock is the sudo password typed in the key bar). `tui/input.rs` is the one input line (`Input<P>`: filter, command, a `PromptLine`; Backspace on nothing closes a filter or command, never a prompt); `tui/modal.rs` has `Choice<E>`, `answer` (Enter/y, Esc/n/q) and `pick`. `ScreenId` (`tui/mod.rs`) is every screen any target has (`Svc` is the server's `5`, `Clients` the network's `2`, in no set yet); each declares a `ScreenSet` (`SCREENS` in its `tui/mod.rs`: strip order, aliases, `from_name` by slug, short name, alias or a 3-letter prefix) and `Keymap::new(&SCREENS, &cfg.keys)` binds only those (`[keys] screen.<slug>` of the other program's screen is skipped quietly). `Cursor` lives there too.
- One window, several targets (`crates/sentry/src/tui.rs`, `crates/sentry-app/src/app.rs`): `sentry` opens this machine plus a slot per server in `server_config.yaml` and per network in `network_config.yaml` (neither file: this machine alone, no strip, today's sentry); `sentry-server [name]` / `sentry-network [name]` the same window on that target (`tui::Open`, `plan_all`). `[targets] show = ["local", "srv:<name>", "net:<name>"]` (core `config::Targets::pick`) orders and hides them; a server or network asked for by name opens even when left out. The strip is in the top bar (`frame::Top.targets`, `TargetTab`, `Mark`; none with one target; names cut, then keys only, when narrow): key, name, `*` at work, `!` needs you, `auto`. Keys are the window's (`Keymap::target`, never `resolve`): `F1`… by place, `{` / `}` round (`[keys] target.<n>`, `target.next`, `target.prev`), taken before the slot except that a character is text where text is typed (`Slot::takes_text`: password, session, chat, input line); `:local`, `:server <name start>`, `:net <name start>` (`Ident.word`; `:net` alone is the Network screen of a target that has one, since a target's screen names come first; `Win.target_cmd`, after the target's own `:` commands and screen names). Each slot has its own keymap, screen set and input line: `Slot::park` swaps them with `Win.keys`/`Win.input`, so inside a flow `w.keys`/`w.input` are always that slot's (a prompt stays with the target that asked, text kept). A slot that never had the window is `asleep`: `App::start` only picks up its run left in progress (`Slot::pickup`); its records, first fetches and review at start come with its first focus (`Slot::shown` → `start`; later focuses → `enter(screen)`).
- Parallel across targets, one after another within one: every slot's events land in it whatever is in view (`App::with`), `App::tick` ticks every slot (run, session limits, timeouts), `next_due` asks every slot; only the slot in view polls for its screen (`Cx.focused`; out of view `Slot::enter` fetches nothing). A run goes on off screen `0` and out of view (no in-view rule; `Ways.auto_polled` is only whether the next auto step is also looked for on ticks). `Slot::needs(line)` → `Needs::{Nothing, Working, You(what)}` is the strip's mark; a slot out of view that comes to `You` is flagged and said once (`App::flag`: "<target> · needs you: <what>"), and never gets keys: its boxes, session window, prompts and password line are drawn and answered only in view (the password prompt names the target when there are several; `C-f` forgets the one in view). Toasts from a slot out of view carry its name (`Win.speaker`). Auto keeps answering out of view what `auto::answers` allows; the rest waits and flags. This machine's reboot ends the TUI (`Ways.reboot_ends_tui`): `wf_exec` holds it while another slot is `Working` (`Win.others_working`, `Slot.reboot_held`; the run's log and the banner say for whom) and `reboot_when_settled` sends it from `tick`. `q` with several targets lists what each has going (`App::quit_box`, `Slot::going`); shutdown is per slot as before. The terminal is handed over only for the slot in view (`App::handed`); the others' events queue. The locks (`runs_turn`, `startable`, one run per target's `runs` root) are per target. Tests: `crates/sentry/src/tests.rs` (`two_with(server, sudo_asks)`: this machine + a synthetic server per test, since runs are kept by name; `local_wf` serialises this machine's runs), `live_two_targets`.
- What can wait (every target): `Rec.can_wait` marks a rule nothing asks for yet (server: `Behind`, updates without a security fix, unknown/track/gone; sentry: Flatpak/toolbox-only updates, tidy cleanup); `rec::needed(recs, everything)` drops those and every `Level::Tidy` row (low findings, tidy tasks) from each screen's `recs(v)` (`View.everything`, `o` → `Effect::Everything`); reviews and Claude get them all (`recs_all` / `view_all`, `every_rec`). A due task absorbs a waiting rule of its `Target` in `finish`, so its row shows. A derived task (cadence, job) that never ran counts `every` from the log's first entry (`tasks::counted_from`); one from tasks.toml is due at once.
- A series (every target): `Maint.ticks` (`maintlist::Ticks`, row keys; Space / `a` / Esc, only rows whose `Verbs.series` is set) → Enter → `Effect::SeriesStart` → `maint::series::Series` in the slot beside `apply` (`slot/series.rs`). `series_go` resolves the row it's at from the live list by key (gone: skipped) and opens it: a session (`Session::start_in_series`: no Brief Enter, `Fx::Next` when it settles done or the user goes on; `Fx::Close` on it stops the series), a workflow (started; `series_run_ended` in `wf_log` / `wf_log_change` goes on or stops, and no `LogNote` is asked while a series runs), an audit; an item's row is just a session (on its ready plan when one is saved; one that answers "wait" is skipped). `series_end` / `series_stop` leave what isn't done ticked and run the one `review_after_run`. The banner row shows `Series::line()` when no workflow banner or visible session does. Tests: `ticked_rows_are_done_one_after_another` in each target's tests (and `…_on_each_target` in the window's).
- Records (`crates/sentry-core/src/tui/records.rs`, every target; `v`, `:log`/`:tasks`/`:plans`/`:reviews`/`:later`): one overlay, sections Tasks · Log · Plans · Reviews · Later; it returns `records::Fx`, mapped in `slot/records.rs` (`records_key`; a target's own rows through `Upkeep::records`/`undo`). Snoozes are `maint::later` (`later.toml` under `maint::root`; old `maint.toml` / `servers/<n>.maint.toml` migrated on load). Over Records, a plan or a review, screen keys and `:` still work.
- Apply with Claude (every target) is one session: `crates/sentry-core/src/apply/` (`plan.rs` the ```` ```sentry-apply ```` plan + `Run`; `session.rs` the state machine Brief → Investigating/Fix → Review → SudoCheck/Password → Applying → Verifying → Settled, returning `Fx` for the app to carry out; `verdict.rs` the ```` ```sentry-verdict ````; `sudo.rs` root edits under /etc, the password `Secret`, `wrap`/`wrap_ready`/`no_prompt`/`detached`) and its window `crates/sentry-core/src/tui/applyview.rs`. Its plan's steps and a workflow run's (screen `0`, both programs) are drawn by `crates/sentry-core/src/tui/stepview.rs`: the header (target · what · auto, then `State::words`: running / waiting on you · Enter … / done / failed), `row` (mark, number, title, kind, time taken), the running step's output under its row (`output`, `running`); `run_rows`/`run_state` for a run, `applyview::state` for a session. Opened by `A` → 1, the Plan view's `A` → 1 and Enter on a by-hand task (`Effect::AskConsent` with an apply `Ask`); the slot holds `apply: Option<Session>` beside `chat` and maps `Fx` in `apply_fx` (`slot/session.rs`; commands through `Host::command`: local `Cmd::host` bash; server: `remote.sh`, edits only local files, `Apply.remote`; local's re-audit after a finding's plan is `Why::Reaudit` → `Effect::Reaudited`). A session whose `Apply.plan` is set (an item; here, a workflow) researches first (`claude::apply_question`: the ledger, the notes, the web), and its plan is kept under that key in `plans/` (`Fx::PlanSave` → `Slot::plan_keep`, the assessment + the plan's block; `plans/done/` when done); a ready plan on disk opens the session on it (`Slot::session_for` → `Session::seeded`: Review at once, the brief sent with the first turn; a document from before, as its workflow with its values); `p` reads the saved plan, `P` starts over (`Effect::PlanAgain`). A `sentry-verdict` with `status = "wait"` settles with nothing changed (`End::Waited`, `Fx::Wait`: later.toml for `again` or 30 days, the plan document `wait`, a `kind = "wait"` log entry). No plan writer: `docview::Writer` writes reviews only. Only start and approve are keys; problems, failed steps and verification go to Claude by themselves; `done` tags the apply log entry `task:<id>`; a verdict's `[follow_up]` becomes a one-time task (`Fx::AddTask`) with `Task.after` (a workflow's next good run, or a wait like `7d`; `tasks::waited`). Tests: `offline` spawns nothing; `apply_answer_for_test`, `apply_step_exit_for_test`/`apply_exit_for_test` drive it.
- One sudo password per target (`crates/sentry-app/src/slot/root.rs`, every target): asked inline once (the session's line, or the same line in the key bar: `Unlock`), when the first thing needs it and `Host::sudo_asks` says sudo wants one; held in `Slot.secret` while the window is open; `C-f`, quit and a password sudo refuses (`sudo::wrong_password` in a step's output) forget it. Everything goes through `Slot::root_cmd`: a workflow's sudo step (`run::How::Root`), a session's, `RunSpec.root` (server actions, kill, the reboot, the local audit's sudo fix), `Effect::RootRead` (inventory, Claude's queued reads: by themselves once it's held). Held: `sudo::wrap_ready` + `Cmd::input_after(READY)` (streamed; over ssh it keeps its pty, the password sent after the ready line with echo off) or `wrap` + `Cmd::input` (captured); not held: `no_prompt` (`sudo -n`). The wrapper puts a `sudo` stand-in on PATH that calls the real one with an askpass helper reading a fifo only the wrapper holds open (fd 9): no argv, env, file or log has the password. Nothing sentry runs for Claude or as a step has a stdin (`exec </dev/null`; `sudo::detached` for plain ones). Stopping a step reaches what runs as root (`sudo::rooted`, the one script behind `wrap` and `no_prompt`): each sudo runs in a session of its own (`setsid`, its group in `$SENTRY_D/k.*`), and the wrapper's HUP/TERM/INT trap signals every group still listed as root through the stand-in, ends the step's own tree (the whole process group only where it leads it, as over ssh: here the group is the program's), waits up to 5 s and kills what stays. `live_sudo_stop` (both containers: streamed over ssh, and no terminal + TERM with `use_pty` on and off). The terminal is handed over only for an editor, a shell step, a pager, `toolbox enter`, Claude Code: never for sudo. `sentry workflow` in a terminal still lets sudo ask there.
- Requests (`claude::requested`): `Grant.whole` is the command as Claude wrote it when Claude Code named only a part (the part is what a grant is for; the whole is shown and run), `Grant.remote` says the gateway refused it (`GATEWAY_ASKS`). `Session::grant`: a server session runs only gateway lines on the server; Claude Code's own refusals there are local (read-only → a grant, changing → refused with why). A request sentry runs is stopped after `Session::ASKED_LIMIT` (120 s, `Slot::tick`).
- Auto (every target; `crates/sentry-core/src/auto.rs`, `crates/sentry-app/src/slot/auto.rs`): `C-a` wherever the keys are toggles `Slot.auto` (off at start, per slot, never saved; `!` would be typed into a session's message). Turning it on asks for the sudo password at once when sudo wants one and none is held (`Waiting::Auto`; Esc or three refusals leave it off; off never forgets the password). The top bar says `· auto`, the banner row too. One pure rule, `auto::answers(auto, &Asked)` (table test there; a new target adds its case, e.g. `Asked::Keep { wifi }`), asked at each decision point by `Slot::auto_step` (after keys, data, `apply_fx`, `wf_cmd`, `wf_auto`): the session's brief, plan and requests (`Session::auto_go`: not while the user types, at most `AUTO_LIMIT` in a row, fix rounds not renewed), a workflow's values when each has a default (`auto_values`, `OwnPrompt.defaults`), its confirm steps (`auto_confirm`: once per step as it stands, `auto_held`), the `LogNote` prompt (`auto_skips_note`), a series' next row. Never: `Next::Reboot`/`Manual`/`Shell`, a step with `risky = true`, a command `auto::never` names anywhere in it as it would run (`claude::workflow_only`, `claude::risky`, firmware and release upgrades), what `claude::grantable` refuses, a `Modal` (actions, kill, cleanup: auto never touches a box), a wrong password, a verdict that isn't done (`auto_series` stops the series, rows left ticked, the session stays open). Those ask as before and say why (`auto leaves … to you`). The one exception: a step with `stage = true`, which lint allows only where `auto::stages_only` (an `rpm-ostree upgrade` without a reboot); quick-update's two staging steps have it, and an edited seeded copy without it keeps asking. Logged: `RunState.auto` (`values`, `step:<id>`, `note`; `WfRun::auto_answered`) → the tag `auto`, "confirmed by auto" in the step's row, an "Answered by auto" section; a session's entry gets the tag and an "Answered by auto:" line. Tests: `auto_*` in each target's tests, `live_auto_series` (both containers).
- Allowing (every target): Claude never asks the user to run or paste anything (`claude::GRANTS`). Every refused call (`claude::refused`) becomes a request and Enter allows it (`Chat::can_allow`; `g` too). `claude::grantable` refuses only keys and passwords, and root's files (a plan's `edit` step). `Grant::changes` (`claude::only_reads`: unknown means changes; git's read-only subcommands count as reads, `git_reads`) is the route: reads and read-only commands become grants and Claude carries on; a local session runs changing and sudo commands itself as a plan of their own (`Session::asked`: the held password, logged, output back to Claude, whose verdict can settle it); a chat hands those to a session; a server session keeps them in plans. Allowed edits of your files are backed up and logged (`Session::edits`).
- A session's Claude runs any command without root (`Profile::acting`, `Asks::profile(ProfileFor::Session, ..)`; chats, plans and reviews keep `Profile::local`): `claude::ASKS_FIRST` are deny rules (sudo, rpm-ostree changes, power, podman rm/stop, ssh, key paths), so those are refused and become requests; in a session every allowed Run request is run by sentry (`Session::grant`), except `claude::workflow_only` (upgrade, rebase, rollback, reboot), which Claude is told to put in a plan as a workflow step. sentry-server: `sentry-server run <name> -- '<line>'` (`gateway::runnable`/`run_cli`, `ask::session_profile`) runs any line as the login user; sudo in it is refused with "requires approval: <line>" (a request, run by `Fx::Command` with the password), power commands and `SECRET` names are never run.
- Reviews started by sentry (every target, `[review] at_start`/`after_run` in config.toml, core `config::Review`): `review_auto` with a quiet `Writer` (no window; what you ask for replaces it), `review::run_ask` after a run that ended well when tasks are still due (once the `LogNote` prompt resolves: `review_after_run`), `review::start_ask` at start once the first data is in (`review_at_start`). `ReviewHead.origin`/`run`. Kept only when it has changes (`auto_review_ended`). `[[done]]` (`Kind::DoneTask`: the app writes `LogEntry::task_found_done`, dated at the run) and `[[again]]` (`Kind::AgainTask` → `Task.again`, due until next done, its why on the row).
- Updates waiting (sentry): Flatpak's are what `flatpak update` would do, answered `n` (`collectors::flatpak::collect_updates`; `remote-ls --updates` over-reports the fedora OCI remote); a count from before the last done quick-update is ignored (`local::still_waiting`, `DataStore::fp_waiting`/`tbx_waiting`); a done quick-update checks again (`recheck_updates`), and a run that ended while sentry was closed is logged at start.
- Pastes (every target): bracketed paste, `Input::Paste` → `on_paste`: the focused input takes it whole, nothing focused ignores it (letters never act as keys). Newlines stay in the message, drawn as ⏎ (`chat::shown_input`).
- Chat: explains only (no proposals, no `r`/`s`; commands are text); `a` hands it to an apply session (`Session::from_chat`, when `Chat::apply_with` is set by `A` → 2). Every fix (a finding, a failed step, a server unit/container) is an apply session (`Apply.finding`: re-audit after the plan; `Apply.step`: Enter retries the step). Opens `pending` (the brief shown, Enter sends; no consent box), follow-ups go as typed. Esc while Claude answers hides it (`Chat::hidden`); `A` brings it back. Both binaries.
- Granting files (every target): a refused tool call (`ToolResult` "…requested permissions…" after a `ToolUse`) becomes `Chat::requests` (`claude::requested`); `g` shows `grant_lines`, `y` → `Effect::ChatGrant` → backup (writes), `Chat::grant`, a follow-up turn. Every turn's profile is base `.with_notes(notes).with_grants(&chat.grants)`: path-scoped `Read/Edit/Write(//p)`, the bare `Edit`/`Write` deny dropped only with a write grant. `claude::grantable`: writes only to files you own (uid of $HOME; anywhere, e.g. /var/mnt); never `.ssh`/`.gnupg`/keyrings/`.password-store`, by path or in a command. After a turn, `Chat::changed` → chat line + log `kind = "edit"`.

## Rules
- **No background processes**: no systemd units, timers or autostart. Threads die with the TUI.
- Every external command goes through `exec::Cmd` (`Cmd::host` for host userspace). Never call `std::process::Command` directly. Dev happens in a toolbox, where `Cmd::host` adds the `flatpak-spawn --host` prefix.
- Host `/etc` is read via `paths::host_root()`.
- Collectors: a pure `parse()` (fixture-tested) and a `collect()` (exec + parse). A missing binary is `CollectError::Unavailable`, never a panic.
- Slow or network collectors run only on `c`/`r` and are cached (`cache.rs`). Nothing refreshes unless its screen is visible.
- Destructive actions: preview → confirm modal → streamed output.
- Never run `rpm-ostree upgrade/rollback/rebase`, `systemctl reboot`, or podman rm/stop for real while developing.

## sentry-server (`crates/sentry-server/src/`, `crates/sentry-server/src/main.rs`)
- A second kind of target (a library; `sentry-server …` is the one program under that name): monitors a server over ssh (`exec::Cmd::ssh`; its `remote::Remote` wraps `sentry_app::remote::Remote` with `cfg` and `inventory` and derefs to it; `workflow.rs` keeps `cond`, `RemoteEnv`, `BUILTINS`, `SEEDS`, `resume`/`begin`; `audit.rs` `derive`/`run`; `gateway.rs` `READ_ONLY`/`allowed`/`runnable`), configured by `~/.config/sentry/server_config.yaml` (sample: `assets/server_config.example.yaml`).
- **The repo is public: nothing about the developer's real server goes into git** (names, IPs, services, containers, ports, disks), nor into commit messages or release notes. Server fixtures in `tests/fixtures/server/` are synthetic (real formats, invented content: `myserver`, `app.service`, `stack`, 192.0.2.x). Captures from the real server go only in the gitignored `tests/fixtures/server/local/`.
- Run `make privacy-check` before every commit and release (patterns live in the gitignored `.private-patterns`).
- Against the real server, only read-only commands while developing; anything that changes it is exercised up to its confirm modal. Mutating mechanics are tested against a disposable local sshd container.
- sudo may ask for a password (the developer's server does): `Host::sudo_asks` (`fresh_sudo`) is looked up again before each thing that needs root; see "One sudo password per target". No terminal handover, nothing tee'd to the server.
- The inventory (`crates/sentry-server/src/inventory.rs`, key `I`): the collectors' own sudo argv run once in one `sudo sh -c` (`Effect::RootRead`, parsed from the command's own output), cached; read again by itself after a run when the password is held; `Remote::output` answers a refused `sudo -n` from it only when `Remote::inventory` is set (the TUI), never for workflow conditions.
- Maintenance (`crates/sentry-server/src/maint/`, screen `6`, `sentry-server maint`): `maintenance:` items in the config; the server's side in `local.rs`, upstream (curl from this machine: GitHub releases, Docker Hub, GHCR, endoflife.date) cached daily in `upstream.rs`, pure `eval.rs` → flags and `srv:maint:*` findings. Snoozes (review dates, `z`) in `servers/<name>/later.toml` (`maint::later`); what was changed is read from the maintenance log. Plans and reviews get WebFetch/WebSearch and Read of the `notes:` files only.
- Claude's reads that need root: the gateway queues them in `$XDG_RUNTIME_DIR/sentry-server/reads-<server>.jsonl` (the runtime dir is the same for the TUI and Claude's child processes); after a turn the TUI runs them in one `sudo sh -c` (`root_reads`: at once when the password is held, else the one prompt, which names them) and sends the output as the next turn. Plans are a session's (see the apply-session paragraph): `apply_plan` → `ask::apply_item` (`Apply.plan` = the item), `Asks::plan_head` gives a new document its header (`maint::plan_doc`), `servers/<name>/plans/<item>.md` (`crates/sentry-core/src/maint/plan.rs`: `+++` TOML header, then Markdown); `planview.rs` is reviews only. The Plan view renders the document; applied, dropped or started over (`P`) plans move to `plans/done/`.
- Processes (`2`, `crates/sentry-server/src/tui/screens/processes.rs`, drawn by core `tui::proctable` like sentry's): `Kind::Procs` (`collect/procs.rs`: the probe script + `id -u` + `ps` + an awk over `/proc/[0-9]*/stat`, one exec without sudo every 2 s while the screen is shown, the second sample after 1 s). `ps`'s %CPU is a lifetime average, so `Rates::procs` computes `100 · cores · Δticks / Δtotal` against the probe's aggregate cpu line (first sample NaN → `–`; a new or reused pid 0; kernel threads left out by `PF_KTHREAD`); the same sample feeds `Store::on_probe`. Sections are cut at lines equal to `@@ps` / `@@ticks`. `x` (kill, as in sentry): a confirm box with `proctable::kill_lines` and the command; the login's own process is `kill -TERM`, another user's goes through sudo (`RunSpec.root`; `Screens::uses_root` looks at the selection so sudo is checked first). `collect::procs::kill_script` first compares `/proc/<pid>/stat`'s start time with the sampled one (`process <pid> is gone` otherwise). pid 1 is refused; an ancestor of the sampling shell (`@@self` = `$$`, parents from the awk's fifth field: `lineage`) is our own ssh session or the ssh server and gets the hard-to-undo warning. Never past the box on a real server; `live_actions` (disposable container) kills a `sleep` through it. Its per-sample cost on a real server is unmeasured.
- History (`H`, `crates/sentry-server/src/tui/screens/history.rs`, drawn by core `tui::histview` like sentry's; in the strip once `ServerTarget::has_ring`): the ring is on this machine, `<data>/servers/<name>/metrics/ring.bin`, sentry's format, fixed 10 s / 72 h (`crates/sentry-app/src/remote/recorder.rs`; the server's `recorder.rs` adds its disks/temperature/GPU sampler). Two writers, both through `ring::append`: the TUI (`ServerTarget::record_sample`: every probe the Dashboard or Processes takes goes through `Recorder::feed`, no extra ssh; not when `offline`, not while `recorder::live(server)`) and the foreground `sentry-server record [server]` (one probe per 10 s, disks/temperature/GPU per minute, pid file removed on Ctrl-C/TERM/HUP; nothing runs on the server, no alerts). `Kind::History` reads the ring from local disk on entry and `r`. Tests never write a ring for `myserver` (offline); the recorder's own tests use per-test server names. `live_record` (`#[ignore]`): `SENTRY_SERVER_LIVE=<name> XDG_DATA_HOME=<scratch> cargo test live_record -- --ignored`.
- Network (`3`, `crates/sentry-server/src/tui/screens/network.rs`, drawn by core `tui::netview` like sentry's): `Kind::Sockets` (`collect/sockets.rs`: one `ss` exec without sudo, every 5 s while the screen is shown; polled sudo would fill the server's auth log) with the names only root sees from `Kind::Listeners` (sudo, or the inventory). One rule with the audit: `audit::listener_status` (local / client / baseline / new; not core's `net::classify`, which hides high UDP ports) decides both the row and the `srv:listener:<proto>:<port>` finding (`audit::listener_id`). What's expected is `servers/<name>/baseline.toml` (core `BaselineFile`: `listeners` + `findings`; the old `servers/<name>.baseline.toml` is moved in on first load), held in the slot's `Shared.baseline` (read at start and after each change; tests write nothing). `b` (`Own::ListenExpected`) marks the port on every address and its finding, `b` again takes both back; no box.
- Maintenance review: `maint/discover.rs` (untracked / gone), `maint/tracked.rs` (`servers/<name>/items.toml`, merged in `Remote::new`), `maint/recommend.rs` (pure rules → ranked recommendations with actions; `maintenance.cadence` entries are derived tasks, `server::maint::cadence_tasks`), `crates/sentry-core/src/maint/review.rs` + `R` (Claude review, same writer as plans; its changes are applied in the review window: tasks to `servers/<name>/tasks.toml`, items through `tracked::apply`, where `untracked` and `[set.<id>]` in items.toml apply over the YAML's items, which are never rewritten). Maintenance is sentry's screen (`maintlist::split`, `detail_head`, `later_choice` 7/30/90 and the shared strings are core's; `e` on a task is `Prompt::TaskEvery` → `tasks::set_every`, `B` a `srv:<kind>:*` pattern via `audit::pattern_for`): recommendations then items (the Items panel, where sentry has Deployments), one cursor; `F`/`:audit` open the audit report view over it (`Maint::view`, `screens/report.rs` builds a `tui::reportview::Page` from `Store::shown`: a report and the one before, `Kind::Report`/`ReportAt` read from disk; sentry's `screens/audit.rs` builds its own `Page` for the same core view); `screens::maint::Maint::sel` keeps the selection on its row when the list changes. Audit findings, package updates and reboots are recommendations there (no Audit/Updates screens); workflows are screen `0` (Upgrade, `crates/sentry-server/src/tui/screens/upgrade.rs`: the list through core `tui/wflist.rs`, shared with sentry's Upgrade; Enter → `Slot::wf_start`: values asked first, else it starts (no start box: Enter was the approval; confirm steps still ask); a run is followed there and goes on whatever is in view, elsewhere the banner; `w` on Maintenance and `:wf` go there). Screens (`tui::SCREENS`, sentry's numbers and names): `1` Dashboard (was Overview; `:overview` still works), `3` Network, `4` Containers, `5` Services, `6` Maintenance, `0` the run. `crates/sentry-server/src/tui/screens/` (`mod.rs`: `View`, `Screens`; one file per screen, each a struct holding a core `Cursor`): the app reaches them through `Screens::{polls, on_enter, handle, render, hints, ask, badge, filterable, uses_root, cur, reset_cursor, clamp}` and `ServerTarget::with_screens`; `polls(screen)` is what is fetched, at entry and every `Poll.every`, only while that screen is in view (`Target::due`). `[keys]` in config.toml is honoured (`Keymap::new(&SCREENS, …)`).
- Maintenance log (`crates/sentry-core/src/maint/log.rs`, shared): every finished workflow run → `servers/<name>/log/<when>-<item>-<workflow>.md` (+++ TOML header with tags, steps table, note) and the `LOG.md` ledger; written when the run ends, rewritten when the note is given. Plans and reviews get Read on the log dir and are told to start from the ledger.
- A server's own workflows: `~/.config/sentry/servers/<name>/workflows/` (local, never in git) replace the seeded generic ones.
- The one background exception: ssh's multiplex master (`ControlPersist=15s`) outlives the last command by at most 15 s, then exits by itself. Streamed and interactive commands (actions, workflow steps) use their own connection: through the shared one, killing the local client leaves the remote command running.
- Test knobs: `SENTRY_SSH_CONFIG=<file>` passes `-F` to ssh (point it at a throwaway sshd without touching ~/.ssh). Local-only live tests (`#[ignore]`, `-p sentry-server`): `SENTRY_SERVER_LIVE=<name> cargo test -p sentry-server live_screens|live_ask -- --ignored --nocapture` (read-only against the real server); `SENTRY_SERVER_LIVE=<name> cargo test live_ask_boxes -- --ignored` (A on the updates recommendation opens the brief, nothing sent; Claude Code checks Read permissions against the resolved path, so notes paths are canonicalized and their dirs passed with `--add-dir`); `SENTRY_SERVER_LIVE=<name> SENTRY_WORKFLOW=<wf> XDG_DATA_HOME=<scratch> cargo test live_preflight -- --ignored` (a workflow's auto steps up to the first confirm, never pressed); `SENTRY_SSH_CONFIG=… SENTRY_SERVER_SCRATCH=<name> XDG_*=scratch cargo test live_actions|live_workflow -- --ignored` (against a disposable sshd container only; `scripts/live-container.sh up|test|down [nopasswd|password]` makes it with podman and runs these, `live_sudo_stop`, `live_auto_series` and, from `crates/sentry`, `live_two_targets`: the container beside this machine, which runs two `echo`s of its own); `live_password_step` and `live_inventory` likewise, against a container whose sudo asks for a password (a fake root-only `docker` printing the synthetic fixtures); they type it into the TUI's prompt (`scripts/live-container.sh up|test|down nopasswd|password`; the password's file is named in `SENTRY_SERVER_SCRATCH_PASSWORD`; `live_claude_reads` too); `cargo test parses_local_captures -- --ignored` (parsers vs gitignored real captures).
- Measured on the real server: the Dashboard at 1 Hz costs 0.67% of one core incl. its ssh commands, 6.9 MB RSS.

## sentry-network (`crates/sentry-network/src/`)
- A third kind of target (a library; `sentry-network …` is the one program under that name, `crates/sentry/src/network.rs`): a home network through its router, OpenWrt over ssh as root. `remote::Router` wraps `sentry_app::remote::Remote` (`Privilege::Root`, scope `net:<name>`, `.dropbear()`) with its `cfg` and derefs to it. Built so far: the config, the collectors, the audit, Dashboard, Clients (`2`), Network (`3`), Maintenance (`6`, findings and tasks) and History, the recorder, the CLI. Maintenance items, updates and backups, Claude and workflows (`0`) are not built: nothing on screen names them (`Asks::offered` is false, so the key bar and `?` offer no Claude and no auto mode).
- **The repo is public: nothing about the developer's real network goes into git** (the router's ssh alias and hostname, SSIDs, addresses, MACs, device names, the ISP), nor into commit messages. Naming a router model as an example of a supported device is fine. Fixtures in `tests/fixtures/network/` are synthetic (real formats, invented content: `home`, `myrouter`, `Example Router AX`, 192.0.2.x / 198.51.100.x / 203.0.113.x, 2001:db8::, MACs 02:00:5e:00:53:xx). Captures from the real router, and the notes on what its busybox can and can't do, are only in the gitignored `tests/fixtures/network/local/` (`NOTES.md`: read it before writing a collector).
- Against the real router only reads while developing: what the collectors run, `sentry-network check|collect|audit|init` with scratch `XDG_*` dirs, and the `#[ignore]` live tests. Never `uci set/commit`, a restart, `apk update/add/del/upgrade`, `owut`, `sysupgrade` (but `-l`), a reboot.
- Dropbear: `ssh -tt` with the local stdin at its end (what `Cmd::stream` does for a server) prints nothing and fails there. `Cmd::hold_stdin()` (set on every command a `Remote::dropbear()` builds) makes `stream` keep a stdin pipe open, unwritten, until the command exits (`Cmd::streamed`: the terminal, and whether stdin is held); stopping the local ssh still ends the remote command (`live_dropbear_stream` in `sentry-app`: gone within the first 250 ms check). Captured commands (`output`) and every other host are untouched. No `nohup`, `timeout`, `sudo`, `ss`, `jq`, `openssl`, `base64`, `curl` on the router, `ps` has no `-o`/`-e`, and busybox `sleep` takes whole seconds.
- Config (`config.rs`): `~/.config/sentry/network_config.yaml` (sample `assets/network_config.example.yaml`), `networks: <name>: { router: { ssh, kind: openwrt }, expect: { zones, forwards, listeners }, devices, thresholds, backup, maintenance: { items, cadence }, notes, claude }`. The whole shape is parsed and linted now (`lint`: names, forwards' proto/port/address, `proto:port@zone` listeners against the zones, MACs via `config::mac`, a `private_mac` device known by hostname, age/ssh recipients, ids and cadences), though only `router` and `thresholds.load`/`mem_pct` are used yet. `Ports` is one port or a range; `local_mac` is the locally-administered bit. sentry never writes the file; `init` writes it once.
- Collectors (`collect/`, each a pure `parse()` + a `collect()`, one ssh exec; `CollectError::Unavailable` for a command that isn't there, via `output_needing`'s `command -v … || exit 127`; `sections` cuts at lines starting `@@`): `probe.rs` = the shared `/proc` probe's files plus `/sys/class/net/*/{carrier,speed}` and the SoC's thermal zone, as one `awk` for the four multi-line files (`cat` each without awk) and the shell's `read` for the rest: no other fork. `Probe { host (the shared `remote::probe::Probe`, flattened), uptime (f64, the router's clock), ports: [Port { name, carrier, speed, rx_bytes, tx_bytes }], temp_c }`; counters are `/proc/net/dev`'s; `speed` is absent on lo and Wi-Fi and without a link (`-1`). `ifaces.rs` = `ubus call system board`, `system info`, `network.interface dump`, `network.device status`: `Board`, `Info` (load ×65536, `root_*` = the overlay in KiB), `Interface` (`gateway`/`gateway6` from the default routes, `lease_time_s` from `data.leasetime`), `Device` (`DevKind` from `devtype`, a Wi-Fi AP is `external` with none; speed from `"1000F"`), `wan()`/`wan6()`, `net_of(dev)` (its own interface, else its bridge's), `rows()` (the uplink's port, the wired ports, the radios; not lo, bridges, or the conduit the switch hangs off). `collect_json` backs `sentry-network collect`.
- More collectors, each one exec, 20–40 ms on the real router: `clients.rs` (`/tmp/dhcp.leases`; `/tmp/odhcpd.leases`, IPv6 by DUID, a MAC only in a DUID-LL; `ip neigh`; each bridge's `brctl showmacs` after an `@bridge <name>` line, its port numbers named through `/sys/class/net/<br>/brif/*/port_no` (hex there, decimal in brctl); per `ubus list 'hostapd.*'` its `get_clients` and `iw dev <if> station dump` for the connected time; → `Raw`; 10 s while Clients is in view). `listeners.rs` (`netstat -lntup` → core `net::Listener`, IPv6 bracketed as `ss` writes it, names cut at 14 as they come; entry and `r`). `uci.rs` (`uci show` one config per call for firewall dropbear uhttpd wireless dhcp network system, then `uci changes`; `parse(text, &Salt)` → `Uci { configs, staged }` with every secret already a tag; views `zones()`, `forwards()` (DNAT redirects, disabled too), `openings()` (ACCEPT rules without a dest), `dropbear()` (password logins on unless off), `uhttpd()`, `wifi()`, `staged_audited()` (only network firewall wireless dhcp dropbear uhttpd; not a dnsmasq option adblock-fast keeps staged beside its own lines); `show()` is the unredacted parser `init` uses for the firewall). `cert.rs` (`hexdump` of `uci get uhttpd.main.cert`, DER; `validity()` walks the ASN.1 to notBefore/notAfter, no crate). `services.rs` (`ubus call service list`; `state()`: `NotADaemon` for the instance-less ones in `NOT_DAEMONS`; `watched()` = dnsmasq, dropbear, uhttpd where installed + `expect.services`).
- Redaction (`redact.rs`): `secret(option)` looks at the option's last name segment only (`key`, `password`, `psk`, `secret`, `token`, `private`, `pin`, `sae_password`, or ending `_<one of them>`; `PasswordAuth` and `key_type` stay readable). `Salt` = 16 random bytes in `networks/<name>/salt` (0600, made on first use); `tag(value)` = `redacted:<8 hex>` of SipHash-2-4 keyed with it (written out here, with the paper's test vector). Nothing unredacted leaves `uci::parse`.
- Clients (`clients.rs`, pure): `merge((leases, leases6), stations, neigh, (fdb, &Topo), &devices, &seen) -> Vec<Client>` keyed by MAC; `Topo::of(&Ifaces)` says which devices are bridges, uplinks (their neighbours are the ISP's, never clients), radios, and each routed device's interface (`Link::Dmz { port, net }`). A device is there by a lease, a station entry, a bridge's table or an answering neighbour (a STALE one only adds addresses). `known` = `devices` names its MAC (an entry without `name:`, as `init` drafts, doesn't); a `private_mac` device's hostname labels a private MAC (never an identity). `unknown()` = not known and not (private on Wi-Fi); `flagged` = unknown, holding a lease, and `Seen` (`networks/<name>/seen.toml`: first, last, lease reads running up to 2) says two reads. `read()` = merge, `Seen::note`, merge. The TUI's store merges once per read (`raw_pending`), saving `seen.toml` when it changed or every 5 min; the audit loads and saves it itself.
- Audit (`audit.rs`, `sentry-network audit [name]`): `Snapshot { ifaces, uci, listeners, clients, cert, services, errors }` (six execs; only ssh failing fails it), pure `derive(snapshot, cfg, prev, baseline)`, reports through `sentry_app::remote::audit` under scope `net:<name>`. `Exposure` (zones, openings, interfaces): `side(listener)` = Local / Any / Zone / Unknown (an address of an interface, the router's own address in an assigned prefix (`Interface.local6`), or a link-local one by EUI-64 when only one zone's devices share that MAC); `wan_open(proto, port)`; `expected_keys` turns `expect.listeners` (`proto:port@zone`) into baseline keys so the shared `listener_status` decides (a socket on every address that the outside can reach needs the uplink's zone named; a UDP port ≥ 32768 is a client's). Findings: `net:wan:down` high; `net:zone:<z>` medium, high when the uplink's zone accepts input or forward; `net:forward:<proto>:<port>` high, `net:forward:missing:<name>` medium; `net:listener:<proto>:<port>` high where the outside reaches it, else low (Tidy: listed with `o`); `net:ssh:password` medium (high when reachable from outside); `net:luci:http` medium; `net:cert:expiry` low within `cert_days`, medium past; `net:config:staged` medium; `net:client:<mac>` medium; `net:service:<name>` high; `net:mem-high` / `net:load-high` (5-min load) medium. `net:config:unsaved` is marked where it goes (needs backups).
- Lease left (`Interface::lease_left`): netifd gives the lease's length and the interface's uptime, and a renewal doesn't restart that uptime. So `Exact(lease − uptime)` only until half the lease has passed; after that `Between(lease/2, lease)` ("renewed, 1h–2h left"). The plan's "lease − uptime" would be negative on any router up for a day.
- Rates (`rates.rs`, pure): `Rates::feed(&Probe)` → per port `Rate { rx, tx }` in bit/s = `Δbytes · 8 / Δuptime`, both the router's. No entry (drawn `–`) on the first sample, a new boot id, a clock that didn't advance, or a port whose counter went back or that is new; `rate_table` is the table. `bits`/`speed` format them. Checked on the real router by `live_rates` (the same two execs also read `/sys/class/net/*/statistics` and `/proc/uptime`, and the two answers must agree within 5 %).
- TUI (`tui/`): `SCREENS` = Dashboard, Clients, Network, Maintenance, History. `target.rs` `NetworkTarget` (`Ident`: id and scope `net:<name>`, word `net`, place "the network", app `sentry-network`; `Ways`: `writer_place: "network"`, `server_changes: false`): `polls(screen)`: Dashboard = `Probe` 1 s, `Ifaces` 30 s, `Services` 60 s, `Report` at entry (this machine's disk); Clients = `Clients` 10 s, `Ifaces`; Network = `Listeners`, `Uci` at entry, `Ifaces`; Maintenance = `Report` at entry, then `Audit` by itself when that report is 7 days old or missing (`audit_on_entry`, in `on_data`), and on `r`/`c`; History = `History`. `Cert` is read when no audit read it within a day; fetched in `enter`, then by `due` only while `cx.focused`; `asked` (tests) lists every fetch asked for. `data.rs` `Store` (`on_probe`: CPU %, memory, `rate`, each port's `traffic` ring for its sparkline, `Sampled` for the recorder; an `Unreachable` error keeps what was last known). `screens/dashboard.rs`: Router (release, board, uptime, load · cpu · temperature, memory and flash bars) and WAN (address, gateway, lease, DNS, IPv6 prefix; "● down") at the left, CPU and uplink graphs under them when there's room, Ports at the right (`port_rows`: link and speed from the probe each second, which interfaces are ports and whose from `Ifaces`; before that has arrived, every interface but lo). `screens/history.rs` is core `tui::histview`.
- Screens (`tui/screens/`, `Screens` holds each one's cursor; `View` has the app's `Shared`): `clients.rs` over core `tui/clientview.rs` (`Row`, `Sort` name/link/signal/lease on `s`, unknown first; `~` a private MAC; `b` toggles `net:client:<mac>` in the baseline; Enter = `Effect::Info` with everything known and the YAML line that names it; no key acts on a device). `network.rs`: Zones and Forwards panels marked by what `audit::derive` says of the firewall as last read (one rule with Maintenance), over core `netview::draw_listening` (no Established panel); `b` = `Own::ListenExpected` (the port's keys + its finding, as on a server). `maint.rs`: `every_rec` = open findings (`Action::Finding`, Enter opens the report on it), the audit when due, tasks through `rec::finish`; `x` (box) / `b` expected, `B` pattern, `z`, `d`/`e`/`m` on tasks, `o`, `F`/`:audit` the report (`report.rs`, core `reportview`), `v` Records; bottom-left is Last audit (what each part found) until there are Items. `dashboard.rs` gained Status: clients (from the last read or audit), services, audit, cert days. `Own::Expected(id|pattern, on)` writes `networks/<name>/baseline.toml` (`findings`), `ListenExpected` its `listeners` too; tests (offline) write nothing.
- Plain answers until they're built (in `tui/target.rs`): `Asks` (`offered()` false; `ask` → Err "Claude isn't set up for a network yet", a profile that allows nothing) and the workflow half of `Host` (no workflows, `begin_run` refuses, `:wf` says so). `Upkeep` is real for findings and tasks: `derived_tasks` none (cadences name workflows), `with_known` the tasks and rows, `records` when it was audited, `undo` takes an expected finding back, `series_step` None (nothing is carried out by sentry yet: Space says so), `changes` → `NoChanges`.
- Recorder: the ring is `<data>/networks/<name>/metrics/ring.bin` (the shared `remote::recorder`, 10 s / 72 h). The TUI feeds it from the Dashboard's probes (`record_sample`: CPU, memory, load, the uplink's bytes/s, the temperature, the overlay's share as the disk; not when `offline`, not while a recorder is live); `sentry-network record [name]` is the foreground loop (the shared `/proc` probe every 10 s, `ubus call system info` and the thermal zone once a minute).
- CLI (`cli.rs`, `init.rs`; `sentry-network [name]` opens the window on that network): `check [name]` (reachable as root, the tools there, release and board, the probe, ports, WAN, then each other collector with its time; exit 1 if something needed is missing), `audit [name]` (findings, the report's path), `collect [kind] [name]` (JSON; every kind without one; `{"unavailable": …}` and exit 3 as `sentry collect`), `lint [name]` (offline), `record [name]`, `init <ssh> [--name N]` (one exec: the ifaces script, `uci show firewall`, `/tmp/dhcp.leases`; `init::draft` is pure: zones and DNAT redirects as `expect`, each lease as an unnamed device, by MAC or, for a locally administered MAC, by hostname; the ports as a comment; written only when `network_config.yaml` isn't there, else printed with exit 1).
- Test knobs (`#[ignore]`, all read-only, with `XDG_CONFIG_HOME`/`XDG_DATA_HOME` at a scratch dir holding a `network_config.yaml`; the audit writes its report, `salt` and `seen.toml` there): `SENTRY_NETWORK_LIVE=<name> cargo test -p sentry-network live_network_screens|live_rates|live_record -- --ignored`; `SENTRY_DROPBEAR_LIVE=<ssh alias> cargo test -p sentry-app live_dropbear_stream -- --ignored` (streams a `sleep`, stops it locally, checks it's gone there: the one thing run on the router that isn't a read).
- Measured (release build, under a pty, the network Dashboard in view for a minute): 0.67% of one core incl. its ssh children and the multiplex master (0.57% without the master), 12.2 MB RSS. On the router (4 cores; `/proc/stat` over a minute with and without the probe running): busy 4.0–4.3% of one core by itself, 5.3–6.2% with the 1 Hz probe, so the probe costs about 1.6% of one core (1.2 and 1.9 in two runs; it was 2.3% with a `cat` per file, which is why the script is one `awk`). The script itself is 4 ms of the roughly 16 ms a sample costs there; the rest is dropbear starting a session and a shell.
