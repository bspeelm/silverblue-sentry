# sentry: Silverblue monitor & maintenance TUI (Rust + ratatui)

Spec: `docs/spec.md`. Binding amendments: `docs/spec-addendum.md` (read both before changing behavior).
Design for M3–M7: `docs/design/m3-m7.md`.
Visual target: `docs/design/sentry-tui.dc.html` (read the source; don't render it).
Upgrade procedures: the user's personal notes in `docs/cheatsheets/` (gitignored, never commit or publish them) are the source for `assets/workflows/*.toml`.

## Layout
- Cargo workspace, one repo: `crates/sentry-core` (shared: exec, paths, config, baseline, finding, claude, maint records, workflow format + runner, disk/gpu/journal/net/procfs parsers, the TUI kit incl. the frame, chat, docview, maintlist, records), `crates/sentry-app` (what targets share beyond the kit: the app itself, below, and `remote/`: a host over ssh), `crates/sentry` (this machine) and `crates/sentry-server`. Core never depends on the others; `sentry-app` depends only on core.
- `sentry` re-exports core under the old names (`crate::exec`, `crate::maint::log`, …); its `maint`, `workflows`, `collectors`, `tui` modules glob-re-export core's and add their own. sentry-server uses `sentry_core::…` explicitly (its own `config`/`maint`/`tui`/`audit` would clash).
- `crates/sentry-app/src/remote/` (moved out of sentry-server, which re-exports them under its old paths): `mod.rs` `Remote { name, host, scope, privilege }` (`Privilege::Sudo { allow }`: `sudo -n` through the allowlist; `Privilege::Root`: bare argv, `sudo_mode()` is `SudoMode::Root` without an exec), `Error` (the server's `SrvError`), `host`; `workflow.rs` (`Session` with a `Box<dyn Env>` and the program's name, `Exec`, `Live`, `tee_to`, `no_prompt`, `root`/`own_dir`/`pick_dir`); `probe.rs`; `recorder.rs` (`record(r, extras)`); `audit.rs` (`Report<S>`, the report store, `set_expected*`, `pattern_for(ns, …)`, `listener_status`/`listener_id`); `gateway.rs` (`SECRET`, `Held`, `words`/`commands`, `run_cli(prog, r, line, policy)`, the read queue); `upstream.rs` (GitHub, endoflife.date, `comparable`).
- `crates/sentry-app/src/` is the app (both binaries run `sentry_app::App`, one slot each): `target.rs` (`Target` with `Upkeep`/`Asks`/`Host`, object-safe: a target owns its fetch threads, kinds, store and screens; `Ident` its names and words; `Ways` where a program's flows go their own way: words and rules such as `auto_in_view`, default = the server's, each flow asks `self.ways`; `Cx` what it may look at, incl. `at`, the one clock (`Win.at`, the event's instant); `Mail` how its threads and streams answer, tagged with its id; hooks with a default for what only one program does: `on_prompt`, `pane_ended`, `plan_key`, `plan_written`, `chat_continue`, `wf_start`, `session_starts`, `run_cmd`, `run_plan`/`run_info`, `find_workflow`), `app.rs` (`App { slots, focus, win }`; `Win`: theme, keymap, toast, the input line, the help/quit box; `Event` carries a target id), `slot.rs` + `slot/` (`Slot`: one target, its `Shared` records, the screen in view, run, session, series, chat, writer, Records, its boxes; every flow is an `impl Slot` method taking `&mut Win`: `core` events/keys/`open()`/prompts, `effects`, `session`, `wf`, `series`, `review`, `records`, `draw`), `shared.rs`, `effect.rs` (`Effect`, `Prompt`, `WfCmd`; a target's own effects travel as `Effect::Own` and come back in `Target::on_own`/`after_suspend`), `run.rs` (`WfRun`: a workflow run as the app sees it; `remote::workflow::Session` is one, sentry's `tui/wf.rs` `Session` the other; `Exec::Stream { dry, timeout }`, `Shell`, `Live.deadline`). Its `testing` feature holds the tests' helpers (`apply_answer_for_test`, `writer_answered`, `render_to_string`…). The server's side: `crates/sentry-server/src/tui/target.rs` (`ServerTarget`, its `Own` effects, `testing::{srv, wf, data_ev}`) + `target/upkeep.rs`; `tui::app(remote, tx)` builds the app. This machine's side: `crates/sentry/src/tui/target.rs` (`LocalTarget`: the store, the schedule, `lift` turns the screens' `tui/app.rs` `Effect`s into the app's or sends them back as `Effect::Own` → `on_local`; reboot, `run_go`, rollback, baseline edits) + `target/upkeep.rs` (lists, Claude's profiles and requests, the workflow plans' box and keys); `tui::app(tx)` builds it; `tui/app.rs` is only the screens' effect types and the tests' `App` wrapper (`for_test`, `*_for_test`).
- A scope (`maint::root`, `maint::data_root`, the ring, baseline): `""` this machine, a plain name `servers/<name>`, `net:<name>` `networks/<name>`; `maint::label` drops the prefix. Never build those paths by hand.
- Test support in core is behind its `testing` feature, enabled only through the other crates' dev-dependencies (scratch XDG dirs, `claude::TEST_AVAILABLE`). Fixtures stay in the root `tests/fixtures/` (`../../tests/fixtures` from a crate).

## Commands
- Build/test: `make check` (= `cargo build --release && cargo test && cargo clippy --all-targets -- -D warnings && cargo fmt --check`)
- Snapshot tests: `cargo insta review` (or `INSTA_UPDATE=always cargo test` and then inspect `git diff`)
- Tests run with `TZ=UTC` (`.cargo/config.toml`), so snapshots match CI; `cargo run` shows UTC times too unless `TZ` is set.
- Unit tests never touch the real config/data/cache: `paths::xdg` gives each test process a scratch root under the temp dir (XDG_* ignored). Live tests (`#[ignore]`) call `crate::paths::use_real_dirs()` first, which honours XDG_* again; a new live test must too.
- CI (`.github/workflows/ci.yml`) runs `make check` plus MSRV (1.95, set by sysinfo) and a privacy scan on every PR. Never push to `main`: branch, PR, the user merges.
- Re-capture fixtures: `scripts/capture-fixtures.sh` (scrubs the username and IPs; journal fixtures are synthetic, never captured)
- Install: `make install-binary` (copies `target/release/sentry` to `~/.local/bin/sentry`)
- Try a collector: `cargo run -q --bin sentry -- collect ostree`; a job plan: `cargo run -q --bin sentry -- job cleanup-flatpak --dry-run` (two binaries: name one, `--bin sentry-server` for the other)
- Manual TUI tests: point `XDG_DATA_HOME`/`XDG_CONFIG_HOME` at a scratch dir so reports, the log, tasks.toml and baseline.toml stay out of the real ones

Allowed edits of your files are backed up and logged (`Session::edits`).

Kept only when it has changes (`auto_review_ended`). `[[done]]` (`Kind::DoneTask`: the app writes `LogEntry::task_found_done`, dated at the run) and `[[again]]` (`Kind::AgainTask` → `Task.again`, due until next done, its why on the row).
- Updates waiting (sentry): Flatpak's are what `flatpak update` would do, answered `n` (`collectors::flatpak::collect_updates`; `remote-ls --updates` over-reports the fedora OCI remote); a count from before the last done quick-update is ignored (`local::still_waiting`, `DataStore::fp_waiting`/`tbx_waiting`); a done quick-update checks again (`recheck_updates`), and a run that ended while sentry was closed is logged at start.
- Pastes (both binaries): bracketed paste, `Input::Paste` → `on_paste`: the focused input takes it whole, nothing focused ignores it (letters never act as keys). Newlines stay in the message, drawn as ⏎ (`chat::shown_input`).
- Chat: explains only (no proposals, no `r`/`s`; commands are text); `a` hands it to an apply session (`Session::from_chat`, when `Chat::apply_with` is set by `A` → 2). Every fix (a finding, a failed step, a server unit/container) is an apply session (`Apply.finding`: re-audit after the plan; `Apply.step`: Enter retries the step). Opens `pending` (the brief shown, Enter sends; no consent box), follow-ups go as typed. Esc while Claude answers hides it (`Chat::hidden`); `A` brings it back. Both binaries.
- Granting files (both binaries): a refused tool call (`ToolResult` "…requested permissions…" after a `ToolUse`) becomes `Chat::requests` (`claude::requested`); `g` shows `grant_lines`, `y` → `Effect::ChatGrant` → backup (writes), `Chat::grant`, a follow-up turn. Every turn's profile is base `.with_notes(notes).with_grants(&chat.grants)`: path-scoped `Read/Edit/Write(//p)`, the bare `Edit`/`Write` deny dropped only with a write grant. `claude::grantable`: writes only to files you own (uid of $HOME; anywhere, e.g. /var/mnt); never `.ssh`/`.gnupg`/keyrings/`.password-store`, by path or in a command. After a turn, `Chat::changed` → chat line + log `kind = "edit"`.

## Rules
- **No background processes**: no systemd units, timers or autostart. Threads die with the TUI.
- Every external command goes through `exec::Cmd` (`Cmd::host` for host userspace). Never call `std::process::Command` directly. Dev happens in a toolbox, where `Cmd::host` adds the `flatpak-spawn --host` prefix.
- Host `/etc` is read via `paths::host_root()`.
- Collectors: a pure `parse()` (fixture-tested) and a `collect()` (exec + parse). A missing binary is `CollectError::Unavailable`, never a panic.
- Slow or network collectors run only on `c`/`r` and are cached (`cache.rs`). Nothing refreshes unless its screen is visible.
- Destructive actions: preview → confirm modal → streamed output.
- Never run `rpm-ostree upgrade/rollback/rebase`, `systemctl reboot`, or podman rm/stop for real while developing.

## sentry-server (`crates/sentry-server/src/`, `crates/sentry-server/src/main.rs`)
- A second binary from the same library: monitors a server over ssh (`exec::Cmd::ssh`; its `remote::Remote` wraps `sentry_app::remote::Remote` with `cfg` and `inventory` and derefs to it; `workflow.rs` keeps `cond`, `RemoteEnv`, `BUILTINS`, `SEEDS`, `resume`/`begin`; `audit.rs` `derive`/`run`; `gateway.rs` `READ_ONLY`/`allowed`/`runnable`), configured by `~/.config/sentry/server_config.yaml` (sample: `assets/server_config.example.yaml`).
- **The repo is public: nothing about the developer's real server goes into git** (names, IPs, services, containers, ports, disks), nor into commit messages or release notes. Server fixtures in `tests/fixtures/server/` are synthetic (real formats, invented content: `myserver`, `app.service`, `stack`, 192.0.2.x). Captures from the real server go only in the gitignored `tests/fixtures/server/local/`.
- Run `make privacy-check` before every commit and release (patterns live in the gitignored `.private-patterns`).
- Against the real server, only read-only commands while developing; anything that changes it is exercised up to its confirm modal. Mutating mechanics are tested against a disposable local sshd container.
- sudo may ask for a password (the developer's server does): sudo is checked again before each sudo step or action; password → terminal handed over, the step's output tee'd to `~/.cache/sentry-server/` on the server and read back into its log; streamed steps get `sudo -n` so they fail instead of waiting on a prompt nobody sees.
- The inventory (`crates/sentry-server/src/inventory.rs`, key `I`): the collectors' own sudo argv run once in one `sudo sh -c` with the password, cached; `Remote::output` answers a refused `sudo -n` from it only when `Remote::inventory` is set (the TUI), never for workflow conditions.
- Maintenance (`crates/sentry-server/src/maint/`, screen `6`, `sentry-server maint`): `maintenance:` items in the config; the server's side in `local.rs`, upstream (curl from this machine: GitHub releases, Docker Hub, GHCR, endoflife.date) cached daily in `upstream.rs`, pure `eval.rs` → flags and `srv:maint:*` findings. Snoozes (review dates, `z`) in `servers/<name>/later.toml` (`maint::later`); what was changed is read from the maintenance log. Plans and reviews get WebFetch/WebSearch and Read of the `notes:` files only.
- Claude's reads that need root: the gateway queues them in `$XDG_RUNTIME_DIR/sentry-server/reads-<server>.jsonl` (the runtime dir is the same for the TUI and Claude's child processes); after a turn the TUI offers them, runs them in one `sudo sh -c` (inventory's capture helpers) and sends the output as the next turn. Plans (`p`) decide (research, target or wait), apply sessions do: Enter on a ready plan opens a session seeded with it (`apply_plan` → `ask::apply_item`; workflow steps carry `vars`, the plan's as base; done → `Fx::PlanDone`). Plans are a separate flow from Ask Claude (prompts and profiles in `crates/sentry-server/src/tui/planview.rs`, the flow in `sentry-app`'s `slot/review.rs` and `slot/records.rs`): their own system prompt (no length cap; answer with only the plan document, `TARGET:` first), a background `Writer` whose final answer (`Done.result`) becomes `servers/<name>/plans/<item>.md` (`crates/sentry-core/src/maint/plan.rs`, re-exported as `server::maint::plan`: `+++` TOML header, then Markdown); the Plan view renders it; applied, dropped or replaced (`P`) plans move to `plans/done/`.
- Processes (`2`, `crates/sentry-server/src/tui/screens/processes.rs`, drawn by core `tui::proctable` like sentry's): `Kind::Procs` (`collect/procs.rs`: the probe script + `id -u` + `ps` + an awk over `/proc/[0-9]*/stat`, one exec without sudo every 2 s while the screen is shown, the second sample after 1 s). `ps`'s %CPU is a lifetime average, so `Rates::procs` computes `100 · cores · Δticks / Δtotal` against the probe's aggregate cpu line (first sample NaN → `–`; a new or reused pid 0; kernel threads left out by `PF_KTHREAD`); the same sample feeds `Store::on_probe`. Sections are cut at lines equal to `@@ps` / `@@ticks`. `x` (kill, as in sentry): a confirm box with `proctable::kill_lines` and the command; the login's own process is `kill -TERM`, another user's goes through sudo (`sudo -n` streamed, or the terminal handed over when sudo asks; `Screens::uses_root` looks at the selection so sudo is checked first). `collect::procs::kill_script` first compares `/proc/<pid>/stat`'s start time with the sampled one (`process <pid> is gone` otherwise). pid 1 is refused; an ancestor of the sampling shell (`@@self` = `$$`, parents from the awk's fifth field: `lineage`) is our own ssh session or the ssh server and gets the hard-to-undo warning. Never past the box on a real server; `live_actions` (disposable container) kills a `sleep` through it. Its per-sample cost on a real server is unmeasured.
- History (`H`, `crates/sentry-server/src/tui/screens/history.rs`, drawn by core `tui::histview` like sentry's; in the strip once `ServerTarget::has_ring`): the ring is on this machine, `<data>/servers/<name>/metrics/ring.bin`, sentry's format, fixed 10 s / 72 h (`crates/sentry-app/src/remote/recorder.rs`; the server's `recorder.rs` adds its disks/temperature/GPU sampler). Two writers, both through `ring::append`: the TUI (`ServerTarget::record_sample`: every probe the Dashboard or Processes takes goes through `Recorder::feed`, no extra ssh; not when `offline`, not while `recorder::live(server)`) and the foreground `sentry-server record [server]` (one probe per 10 s, disks/temperature/GPU per minute, pid file removed on Ctrl-C/TERM/HUP; nothing runs on the server, no alerts). `Kind::History` reads the ring from local disk on entry and `r`. Tests never write a ring for `myserver` (offline); the recorder's own tests use per-test server names. `live_record` (`#[ignore]`): `SENTRY_SERVER_LIVE=<name> XDG_DATA_HOME=<scratch> cargo test live_record -- --ignored`.
- Network (`3`, `crates/sentry-server/src/tui/screens/network.rs`, drawn by core `tui::netview` like sentry's): `Kind::Sockets` (`collect/sockets.rs`: one `ss` exec without sudo, every 5 s while the screen is shown; polled sudo would fill the server's auth log) with the names only root sees from `Kind::Listeners` (sudo, or the inventory). One rule with the audit: `audit::listener_status` (local / client / baseline / new; not core's `net::classify`, which hides high UDP ports) decides both the row and the `srv:listener:<proto>:<port>` finding (`audit::listener_id`). What's expected is `servers/<name>/baseline.toml` (core `BaselineFile`: `listeners` + `findings`; the old `servers/<name>.baseline.toml` is moved in on first load), held in the slot's `Shared.baseline` (read at start and after each change; tests write nothing). `b` (`Own::ListenExpected`) marks the port on every address and its finding, `b` again takes both back; no box.
- Maintenance review: `maint/discover.rs` (untracked / gone), `maint/tracked.rs` (`servers/<name>/items.toml`, merged in `Remote::new`), `maint/recommend.rs` (pure rules → ranked recommendations with actions; `maintenance.cadence` entries are derived tasks, `server::maint::cadence_tasks`), `crates/sentry-core/src/maint/review.rs` + `R` (Claude review, same writer as plans; its changes are applied in the review window: tasks to `servers/<name>/tasks.toml`, items through `tracked::apply`, where `untracked` and `[set.<id>]` in items.toml apply over the YAML's items, which are never rewritten). Maintenance is sentry's screen (`maintlist::split`, `detail_head`, `later_choice` 7/30/90 and the shared strings are core's; `e` on a task is `Prompt::TaskEvery` → `tasks::set_every`, `B` a `srv:<kind>:*` pattern via `audit::pattern_for`): recommendations then items (the Items panel, where sentry has Deployments), one cursor; `F`/`:audit` open the audit report view over it (`Maint::view`, `screens/report.rs` builds a `tui::reportview::Page` from `Store::shown`: a report and the one before, `Kind::Report`/`ReportAt` read from disk; sentry's `screens/audit.rs` builds its own `Page` for the same core view); `screens::maint::Maint::sel` keeps the selection on its row when the list changes. Audit findings, package updates and reboots are recommendations there (no Audit/Updates screens); workflows are screen `0` (Upgrade, `crates/sentry-server/src/tui/screens/upgrade.rs`: the list through core `tui/wflist.rs`, shared with sentry's Upgrade; Enter → `Slot::wf_start`: values asked first, else the start box; a run is followed there, its auto steps run only while `0` is in view, elsewhere the banner; `w` on Maintenance and `:wf` go there). Screens (`tui::SCREENS`, sentry's numbers and names): `1` Dashboard (was Overview; `:overview` still works), `3` Network, `4` Containers, `5` Services, `6` Maintenance, `0` the run. `crates/sentry-server/src/tui/screens/` (`mod.rs`: `View`, `Screens`; one file per screen, each a struct holding a core `Cursor`): the app reaches them through `Screens::{polls, on_enter, handle, render, hints, ask, badge, filterable, uses_root, cur, reset_cursor, clamp}` and `ServerTarget::with_screens`; `polls(screen)` is what is fetched, at entry and every `Poll.every`, only while that screen is in view (`Target::due`). `[keys]` in config.toml is honoured (`Keymap::new(&SCREENS, …)`).
- Maintenance log (`crates/sentry-core/src/maint/log.rs`, shared): every finished workflow run → `servers/<name>/log/<when>-<item>-<workflow>.md` (+++ TOML header with tags, steps table, note) and the `LOG.md` ledger; written when the run ends, rewritten when the note is given. Plans and reviews get Read on the log dir and are told to start from the ledger.
- A server's own workflows: `~/.config/sentry/servers/<name>/workflows/` (local, never in git) replace the seeded generic ones.
- The one background exception: ssh's multiplex master (`ControlPersist=15s`) outlives the last command by at most 15 s, then exits by itself. Streamed and interactive commands (actions, workflow steps) use their own connection: through the shared one, killing the local client leaves the remote command running.
- Test knobs: `SENTRY_SSH_CONFIG=<file>` passes `-F` to ssh (point it at a throwaway sshd without touching ~/.ssh).
